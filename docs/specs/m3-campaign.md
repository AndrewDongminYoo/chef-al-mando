# M3 구현 명세: 고정 캠페인과 엔딩

작성일: 2026-09-08.
상태: M3 명세 작성·구현 승인, 로컬 구현 중.
기준 커밋: `9bfc1687c07e01c814fcaaea9d0912cfda7f4fc6`.

## 1. 승인과 검증 경계

운영자는 시나리오 선택·목표 판정·해금·재도전을 먼저 연결하고, 서로 다른 운영 문제를 가진 콘텐츠와 엔딩을 완성하는 M3 명세 작성과 구현을 승인했습니다.
운영자는 사용자 5명 검증을 본인이 “이 정도면 테스트 진행해도 좋겠다”라고 말할 때까지 보류하도록 지시했습니다.
이는 M3 착수 예외이며 M2 재미 검증 통과나 사용자 관찰 결과를 뜻하지 않습니다.
에이전트는 참가자를 모집하거나 사용자 검증을 자동으로 재개하지 않습니다.
Android 실기기 검증 보류도 유지합니다.

이번 범위는 로컬 명세·구현·검증입니다.
커밋·푸시·PR·머지와 새 실기기 설치·실행은 별도 요청 범위로 남깁니다.
기존 작업 폴더와 실기기 설치본을 보존합니다.

기준은 [블루프린트](../plans/PLAN.md), [M2 명세](m2-preparation.md), 머지된 정비 PR #5입니다.
Oracle의 개인 계정 `chef-al-mando` 조회에서 `campaign progression`, `campaign records`와 관련된 적용 가능한 선례는 `[no precedent found]`였습니다.
검색 결과의 위키 리비전 최신성은 확인되지 않았으므로 추가 근거로 사용하지 않습니다.

## 2. 완성할 플레이 흐름

앱을 실행하면 여덟 영업의 목록과 현재 해금·완료·최고 기록을 표시합니다.
첫 영업은 항상 열려 있습니다.
선택한 영업의 운영 문제, 메뉴 구성, 고정 예산, 직원·설비 수와 목표를 읽고 준비 화면에 들어갑니다.
기존 발주·프렙·배치·담당·우선순위·일시정지·배속 조작을 사용합니다.
300초 마감 후 실제 제공 수와 손익으로 목표를 판정합니다.
성공하면 바로 다음 영업 하나를 해금하고, 마지막 영업 성공 시 엔딩을 표시합니다.
이후에도 완료한 영업을 다시 선택하고 최고 기록을 개선할 수 있습니다.

목표는 `최소 제공 수 이상`과 `최소 손익 이상`을 모두 충족하는 것입니다.
시뮬레이션이 정상적으로 마감되기 전에는 성공 판정이나 기록 갱신을 하지 않습니다.
같은 마감 결과를 화면에서 반복 읽어도 진행이나 기록을 중복 반영하지 않습니다.
실패한 재도전이 기존 완료 기록과 최고 기록을 낮추지 않습니다.
최고 제공 수와 최고 손익은 각각 독립적인 기록이며 한 번의 동일한 시도에서 나온 점수라고 표시하지 않습니다.

재도전은 같은 영업의 마지막 준비 선택으로 돌아갑니다.
다른 영업을 선택하면 그 영업의 기본 준비를 사용합니다.
현금·손실·재고는 영업 사이에 이월하지 않습니다.
진행 중 목록으로 돌아갈 때는 먼저 일시정지하고, 현재 영업을 포기한다는 확인을 표시합니다.
확인을 취소해도 자동 재개하지 않습니다.

## 3. 콘텐츠 계약

M1·M2 fixture는 그대로 유지합니다.
M3는 `content/campaign/`의 정적 `Resource`를 사용합니다.
`ScenarioDef`는 기존 `Definitions`를 확장해 제목·브리핑·운영 문제·목표·고정 주문 메뉴 순서를 소유합니다.
기존 시뮬레이션의 생성자와 명령·snapshot API는 유지합니다.
시나리오 ID에 따라 결과를 바꾸는 분기를 시뮬레이션이나 UI에 추가하지 않습니다.

초기 캠페인은 아래 여덟 영업을 순서대로 구성합니다.
주방 레이아웃은 3종, 직원은 최대 4명, 설비는 최대 6개와 기존 4역할을 사용합니다.
모든 영업은 고정 seed, 100 ms tick, 마감 tick 3000을 사용합니다.
직원 충돌, 통로 예약, 새로운 조리 공정, 숙련도 성장 경제를 추가하지 않습니다.

메뉴는 채소 샐러드, 곡물 수프, 단백질 구이, 곡물 샐러드, 버섯 샐러드, 버섯 수프, 곡물 볶음, 단백질 덮밥의 8종입니다.
기존 수거·손질·조리·제공 공정을 조합합니다.
원재료는 채소·곡물·단백질·버섯 4종이고, 메뉴별 중간 재료 8종을 더해 전체 재료 정의를 12종 이내로 유지합니다.
기존 대표 아트의 규격과 조리 유형 아이콘을 재사용하고 메뉴 이름을 항상 함께 표시합니다.
메뉴별 장편 애니메이션이나 브랜딩 작업은 포함하지 않습니다.

주문 수·메뉴·도착 간격·대기 한도·구매 수량·목표는 정적 데이터에 명시합니다.
각 영업에는 시작 가능한 기본 준비와 목표를 통과하는 재현 가능한 정책 fixture가 있어야 합니다.
초기 예산·목표 수치는 구현 중 실제 시뮬레이션으로 조정할 수 있으며 최종 값과 조정 근거를 실행 기록에 남깁니다.
이 조정은 영업 수·공정·자원 상한을 바꾸지 않습니다.
서로 다른 운영 문제는 브리핑 문구만으로 판단하지 않습니다.
프렙, 발주, 배치, 담당, 우선순위를 바꾼 비교에서 실제 결과 또는 대기·이동 집계가 달라지는지 확인합니다.
자동 비교를 사람의 재미 평가로 해석하지 않습니다.

중복 시나리오·메뉴 ID, 누락된 참조, 잘못된 순서·목표, 메뉴 밖 주문, 자원 상한 초과, 잘못된 기본 준비·경로를 거부합니다.
일부 데이터만 로드된 상태에서 조용히 영업을 생략하거나 잠금을 해제하지 않습니다.

## 4. 캠페인 상태와 기록

`sim/campaign_progress.gd`의 `RefCounted`가 선택 가능한 영업, 결과 판정, 완료 여부, 최고 기록과 엔딩 조건을 소유합니다.
화면은 이 상태를 읽고 명령을 전달합니다.
해금은 앞선 영업의 완료 여부로 계산하며 화면 인덱스나 저장 파일의 임의 잠금 해제 숫자를 신뢰하지 않습니다.
기록을 읽을 때 뒤 영업만 완료된 불연속 진행을 거부합니다.

`persistence/campaign_store.gd`는 `user://campaign_records.json`만 관리합니다.
이는 영업 snapshot이 아닌 캠페인 기록 전용 파일입니다.
M4의 현재 tick·주문·재고·예약·이동·PRNG 상태를 포함한 중간 저장 형식과 구분합니다.
세션 중간 강제 종료 시 현재 영업은 복원하지 않으며 저장한 완료 기록은 유지합니다.

기록 형식은 `schema_version`, `content_version`, `sim_version`, `records`를 사용합니다.
세 버전의 초기 값은 각각 정수 1입니다.
`records`는 시나리오 ID를 키로 쓰고, 각 값에 `completed`, `best_served`, `best_profit`을 저장합니다.
ID·필드·불리언·유한한 정수·범위와 진행 순서를 검사합니다.
알 수 없는 미래 버전은 덮어쓰지 않으며 저장 불가 이유를 표시합니다.

정상 마감 경계에서 임시 파일을 쓴 뒤 다시 읽어 검증합니다.
기존 정상 파일을 백업으로 보존한 뒤 임시 파일을 주 파일로 교체합니다.
쓰기·검증·교체 실패를 성공으로 표시하지 않습니다.
저장 실패 시 세션의 결과를 보존하고 저장 재시도를 제공합니다.
손상·주 파일 누락과 백업 존재를 구분해 백업 복구를 제안하며 자동 복구하지 않습니다.
손상된 기록을 조용히 초기화하지 않습니다.
복구할 수 없으면 원본을 보존한 채 저장 없이 새 캠페인을 플레이할 수 있음을 명시합니다.
미래 버전에는 백업 복구로 덮어쓰는 우회도 허용하지 않습니다.

## 5. 화면과 입력 경계

`presentation/campaign.tscn`을 새 진입 장면으로 사용합니다.
캠페인 목록·브리핑·완료·엔딩·복구 안내는 `presentation/campaign_screen.gd`가 표시합니다.
영업 자체는 기존 `presentation/main.tscn`을 인스턴스화합니다.
주 화면은 필요 시 전달받은 시나리오 정의를 사용하고 정상 마감 snapshot을 신호로 게시합니다.
기존 `scenario_path` 사용법과 단독 영업 검사를 유지합니다.

휴대폰 목록은 스크롤할 수 있고, 잠금 상태는 문구와 버튼 상태로 함께 표시합니다.
브리핑과 결과에는 실제 목표·실적·저장 상태를 표시합니다.
키친 중앙, 측면 주문 목록, 고정 시간 제어와 태블릿 병렬 패널을 유지합니다.
네 직원의 담당 조작과 여덟 메뉴의 프렙 행이 보이며 필요한 행에 스크롤로 접근할 수 있어야 합니다.
배경 전환 시 자동 정지·복귀 후 수동 재개를 유지합니다.
안전 영역과 한글 줄바꿈은 실제 렌더로 확인합니다.
