# M0·M1 구현 명세

작성일: 2026-09-07 · 버전: 0.1 · 상태: 구현 승인, Android 실기기 구매 대기

## 1. 목적과 범위

[확정 블루프린트](../plans/PLAN.md)를 양 플랫폼에서 실행할 수 있는 빈 주방 M0와 한 번의 영업 M1으로 구체화합니다.
본 문서의 새 수치와 세부 규칙은 구현을 위한 제안이며 플레이테스트 결과가 아닙니다.
실행 순서는 [구현 계획](../plans/m0-m1-implementation.md)에 둡니다.

M0는 가로 화면, 터치, 안전 영역, 배경 전환과 복귀, Android·iOS export를 포함합니다.
M1은 고정 주방 하나, 직원 2명, 설비 4개, 메뉴 3종, 주문 20건, 300초 영업, 우선순위·담당·취소 조작과 마감을 포함합니다.
프렙과 배치 편집 UI, 발주 편집, 캠페인, 대표 아트, 중간 저장, 설정·번역 제품화는 후속 단계에 둡니다.
M1은 준비 요약 화면에서 고정 조건을 확인하고 시작하며, 마감 후 같은 조건으로 재시작합니다.

## 4. M1 고정 콘텐츠

### 4.1 시나리오와 경제

시나리오 ID는 `m1_first_service`, seed는 `42`, 초기 tick은 `0`, 종료 tick은 `3000`입니다.
모든 수량·금액·작업 시간은 정수입니다.
금액 단위는 게임 내 원이며 실제 판매 가격과 무관합니다.

| 재료 ID     | 초기 구매 수량 | 단가 | 구매 비용 |
| ----------- | -------------- | ---- | --------- |
| `vegetable` | 22             | 100  | 2200      |
| `grain`     | 8              | 150  | 1200      |
| `protein`   | 8              | 400  | 3200      |

시작 예산은 10000, 구매 재료비는 6600, 직원 2명의 합계 고정 인건비는 2000입니다.
M1은 구매량과 인건비를 편집하지 않습니다.
손익은 `served_revenue - 6600 - 2000`, 종료 현금은 `10000 + profit`입니다.
소비 후 취소한 재료와 남은 재고의 비용은 폐기 내역에 표시하지만 손익에서 추가 차감하지 않습니다.

### 4.2 메뉴와 공정

| 메뉴 ID | 이름        | 재료                       | 조리 역할 | 조리 tick | 매출 | 대기 한도 tick |
| ------- | ----------- | -------------------------- | --------- | --------- | ---- | -------------- |
| `salad` | 채소 샐러드 | `vegetable: 1`             | `cold`    | 60        | 500  | 400            |
| `soup`  | 곡물 수프   | `vegetable: 2`, `grain: 1` | `hot`     | 140       | 900  | 600            |
| `grill` | 단백질 구이 | `protein: 1`               | `hot`     | 240       | 1500 | 800            |

모든 메뉴는 `pickup` 10 tick → 메뉴별 `cook` → `serve` 10 tick의 선형 공정입니다.
이동 시간은 공정 시간에 더해집니다.
원재료 전부를 첫 `pickup` 배정 시 예약하고 실제 `pickup` 공정 시작 시 한 번 차감합니다.
이후 조리와 제공에서는 같은 원재료를 다시 차감하지 않습니다.
중간 결과물은 주문 하나에만 귀속되며 다른 주문이 재사용하지 않습니다.

### 4.3 주방과 직원

격자는 12×8이며 좌상단이 `(0, 0)`입니다.
외곽 `x=0`, `x=11`, `y=0`, `y=7`은 벽입니다.
설비 타일도 장애물이고 나머지 내부 타일은 통로입니다.

| 설비 ID      | 역할      | 설비 타일 | 작업 위치 |
| ------------ | --------- | --------- | --------- |
| `storage_01` | `storage` | `(2, 1)`  | `(2, 2)`  |
| `cold_01`    | `cold`    | `(5, 1)`  | `(5, 2)`  |
| `hot_01`     | `hot`     | `(8, 1)`  | `(8, 2)`  |
| `pass_01`    | `pass`    | `(9, 5)`  | `(9, 4)`  |

직원 `employee_01`, `employee_02`는 `(2, 4)`, `(3, 4)`에서 시작합니다.
둘의 숙련도와 이동 속도는 동일하며 한 타일에 5 tick을 사용합니다.
위치는 타일과 간선 진행량 `0..4`로 표현하며 통로와 직원 위치의 중복을 허용합니다.
작업 위치 예약만 독점합니다.

초기 담당은 모두 `all`입니다.
담당 선택은 `all`, `cold`, `hot`, `off`이며 주문의 조리 역할을 기준으로 해당 주문의 모든 공정에 적용합니다.
`off`는 신규 공정 배정을 받지 않는 상태입니다.
M1은 배치 편집 UI 없이 고정 배치를 사용하지만 데이터로 도달 불가 배치를 주입하는 경로 회귀 테스트는 포함합니다.

## 5. 시뮬레이션 계약

### 5.1 tick과 종료

초기 상태 `tick=0`에는 주문이 없고, 한 번의 `step()`은 다음 tick을 처리합니다.
각 tick은 명령 → 도착·만료 → 공정 완료 → 신규 배정 → 이동 → 이벤트 순서를 유지합니다.
`tick=3000`에서는 도착·만료 단계에서 영업을 닫고 남은 활성 주문을 `expired`, 이유 `service_closed`로 정리합니다.
이 tick에서는 공정 완료·신규 배정·이동을 수행하지 않습니다.
일반 만료 이유는 `deadline`이며 마감과 겹치면 `deadline`을 우선합니다.
3000에 완료 예정인 제공도 성공하지 못합니다.
이미 제공·취소·만료한 주문의 상태와 매출은 다시 바뀌지 않습니다.

공정이 `t`에 시작하고 지속 시간이 `d`이면 완료 예정 tick은 `t+d`입니다.
이동 단계에서 도착한 직원은 다음 tick 신규 배정 단계에서 공정을 시작할 수 있습니다.
이는 이미 확보한 배정의 시작 처리이며 두 번째 작업 배정이 아닙니다.
이 규칙을 첫 구현의 경계 테스트에 고정합니다.

### 5.2 명령과 일시정지

시뮬레이션 명령은 `set_priority`, `set_duty`, `cancel_order`로 제한합니다.
각 명령에는 `apply_tick`, 전역 증가 `sequence`, 대상 ID, 값을 담습니다.
우선순위는 `0..2`이며 높은 숫자가 먼저입니다.
기본값은 `1`입니다.
존재하지 않는 대상, 범위 밖 값, 이미 지난 tick, 중복 sequence는 거부하며 상태를 바꾸지 않습니다.
거부 결과도 UI에 전달합니다.
동일 tick 명령은 sequence 순으로 적용하고 종료 주문 대상 명령은 거부합니다.

UI 입력은 기본적으로 `현재 tick + 1`에 예약합니다.
일시정지 중에도 명령을 예약할 수 있고 UI에는 적용 대기 상태를 표시합니다.
재개하면 예약한 명령이 sequence 순으로 적용됩니다.
일시정지와 배속은 tick 공급기의 제어이며 핵심 시뮬레이션 명령과 구분합니다.
영업 중 restart 대신 취소 조작을 사용하고, 마감 후 restart는 새 시뮬레이션 인스턴스를 만듭니다.

tick 공급기는 정수 마이크로초 누적량을 사용합니다.
배속은 누적량에 `1`, `2`, `4`를 곱하고 100000µs마다 한 tick을 공급합니다.
초기 프레임 처리 상한은 8 tick을 측정용 제안값으로 시작하며 잔여 누적량을 보존합니다.
프로파일 결과에 따라 이 상한만 조정하고 tick은 버리지 않습니다.
일시정지 동안의 벽시계 시간은 누적하지 않으며 복귀 시 배경 체류 시간을 따라잡지 않습니다.

### 5.3 배정·예약·소비

배정 후보는 우선순위 내림차순, 마감 tick 오름차순, `order_id + phase_index` 오름차순으로 정렬합니다.
직원과 설비의 동률은 문자열 ID 오름차순으로 해소합니다.
불가능한 첫 후보 때문에 뒤의 실행 가능한 후보를 막지 않습니다.

배정은 담당 직원, 목적 설비와 작업 위치, 필요한 경로, 미예약 재고를 먼저 확인하고 모두 유효할 때 한 번에 확정합니다.
첫 공정의 예약은 `available = on_hand - reserved`만 줄입니다.
`pickup` 시작 시 `on_hand`와 `reserved`에서 동일 수량을 차감하며 주문에 소비 기록을 남깁니다.
공정 완료 시 직원과 해당 설비 예약을 해제하고 다음 공정을 대기열에 넣습니다.
공정 사이에 이전 설비를 계속 잡고 기다리지 않습니다.

중간 결과물의 위치는 직전 공정 작업 위치로 주문 상태에 남깁니다.
다음 공정을 맡은 직원은 현재 위치 → 중간 결과물 위치 → 목적 작업 위치 순으로 이동합니다.
결과물 수거는 추가 공정 시간이 없고 주문 소유권으로 중복 수거를 방지합니다.
주문은 다음 목적지 하나만 예약하며 이전 작업 위치는 통과할 수 있습니다.
이 방식으로 담당 변경 시 결과물을 순간이동시키거나 여러 작업대를 함께 잡지 않습니다.

이동 중인 배정도 현재 공정에 포함합니다.
담당 변경은 마지막 요청 값을 보관했다가 현재 공정 완료 후 적용합니다.
유휴 직원에게는 즉시 적용합니다.
취소·만료로 배정이 끝날 때도 보류한 담당 변경을 적용합니다.

취소·만료는 직원과 작업 위치의 예약 및 미소비 원재료 예약을 모두 해제합니다.
소비한 원재료는 돌려주지 않고 주문 소유 결과물도 폐기합니다.
이동 중 취소된 직원은 현재 간선의 출발 타일에 남기고 진행량을 0으로 초기화합니다.
이 규칙은 종료 시 정리와 경로 실패에도 적용합니다.

런타임 경로 실패는 현재 배정을 해제하고 해당 공정을 대기로 돌립니다.
원재료를 아직 소비하지 않았다면 재고 예약도 해제하고 재배정 시 다시 검사합니다.
소비 후 실패한 경우 소비 기록과 결과물 위치를 유지하여 다시 차감하지 않습니다.
결과물을 수거한 상태에서 실패하면 직원의 복구된 타일 위치에 결과물을 남깁니다.
수거 전 실패하면 기존 결과물 위치를 유지합니다.
수거 여부도 주문 상태에 기록합니다.
대기 사유는 재료 부족 → 담당 없음 → 작업대 사용 중 → 경로 없음 순으로 처음 실패한 조건을 표시합니다.
유효 담당자가 이미 다른 일을 하는 경우 `담당 없음`에 상세 설명 `담당 직원 작업 중`을 표시합니다.
이동·진행 중 공정은 대기 사유를 표시하지 않습니다.

### 5.4 경로와 결정론

`AStarGrid2D`는 대각선 없이 정적 경로를 계산합니다.
격자 구성과 질의 순서를 고정하고 직원 충돌 회피를 추가하지 않습니다.
동일 엔진 버전에서 같은 입력의 타일 경로가 반복 일치하는지 테스트합니다.
작업 위치가 벽이거나 모든 직원 시작점에서 도달 불가하면 콘텐츠 로드를 거부합니다.

최종 상태 해시는 tick, 일정 커서, 주문·공정·재고·직원·예약·이동·손익, 보류 명령, 보류 담당, 사용한 경우 PRNG 상태를 포함합니다.
객체 주소, UI 상태, 보간값, 실제 시간은 제외합니다.
ID 순으로 배열을 정렬한 명시적 canonical 직렬화를 사용하며 Dictionary 순회나 기본 객체 문자열에 의존하지 않습니다.

## 6. 화면과 M1 수용 기준

콘텐츠 로드 시 중복 ID, 누락 참조, 음수 수량, 0 이하 공정 시간, 순환 공정, 없는 설비 역할, 판매 불가능 메뉴를 거부합니다.
형식 검증은 실제로 잘못된 정의를 넣은 fixture로 확인합니다.

준비 화면은 메뉴·재고·예산과 고정 주방을 표시합니다.
영업 화면은 주방, 남은 시간, 주문별 상태·마감·우선순위, 직원별 담당·대기 사유를 표시합니다.
우선순위 올림·내림, 주문 취소, 담당 선택, 일시정지·재개·배속은 탭으로 수행합니다.
마감에는 제공·취소·만료 건수, 제공률, 매출, 구매비, 인건비, 폐기 비용과 손익을 표시합니다.
M2의 대기 원인별 누적 시간 분석 화면은 여기서 구현하지 않습니다.

| ID    | 조건                                        | 기대 결과                                                           |
| ----- | ------------------------------------------- | ------------------------------------------------------------------- |
| M1-01 | 기본 fixture를 입력 없이 3000 tick 실행     | 20건 도착, 모든 주문 종료, 메뉴마다 최소 1건 제공, 예약·활성 작업 0 |
| M1-02 | 동일 seed와 명령 로그를 두 번 실행          | canonical 상태 해시와 결과가 같음                                   |
| M1-03 | 동일 명령 로그를 1배·4배 tick 공급기로 실행 | 3000 tick에서 해시가 같고 누적 tick 유실 없음                       |
| M1-04 | 직원 2명이 재고 마지막 1개를 동시에 요구    | 하나만 예약·소비, 음수 재고와 이중 배정 없음                        |
| M1-05 | 제공 완료와 기한이 같은 tick                | 만료, 매출 0                                                        |

| M1-07 | 담당 변경을 이동·조리 중 요청               | 현재 공정 유지, 다음 공정부터 새 담당 적용                          |
| M1-08 | 경로 실패를 배정 후 주입                    | 배정 해제, 경로 사유 표시, 소비 재발생 없음                         |
| M1-09 | 기본 fixture의 재료를 고갈시킨 변형         | 재료 부족 표시, 배정 실패 시 부분 예약 없음                         |
| M1-10 | 마감 후 같은 조건 재시작                    | tick·재고·명령·주문 모두 초기화, 이전 매출 이월 없음                |
| M1-11 | 일시정지 중 여러 명령 후 재개               | 정지 중 상태 불변, 다음 tick에 sequence 순 적용                     |
| M1-12 | 양 실기기에서 영업 완주 및 배경 전환        | 터치 조작, 정지 유지, 마감 정산을 실제 화면에서 확인                |

추가 규칙 검사에는 우선순위·마감·ID 동률 해소, 잘못된 명령 거부, 종료 주문 중복 제공 방지, 수거 전후 경로 실패를 포함합니다.
테스트는 만료·취소·경로 실패를 실제로 발생시키는 별도 fixture를 사용합니다.
기본 fixture만 실행해서 경계 조건을 검증했다고 보고하지 않습니다.
M1-01의 최소 제공 기준을 못 맞추면 경로·시간·배정 원인을 조사하고 수치 변경 이유를 명세에 기록합니다.

## 7. 검증 명령 계약

다음 경로와 명령은 구현할 계약이며 아직 존재하는 runner나 성공 결과가 아닙니다.
외부 테스트 프레임워크는 추가하지 않고 `tests/run_tests.gd`가 명시적으로 테스트를 등록합니다.
테스트 runner 자체는 `SceneTree`를 사용할 수 있지만 테스트 대상 `sim/` 객체는 사용하지 않습니다.
테스트 0건, 필수 suite 누락, 실패 assertion은 비정상 종료해야 합니다.

저장소 루트에서 `GODOT_BIN`을 검증된 엔진의 절대 경로로 설정한 뒤 사용합니다.
로컬 예시는 다음과 같습니다.

```bash
export GODOT_BIN=/Applications/Godot.app/Contents/MacOS/Godot
"$GODOT_BIN" --version
bash scripts/check.sh m0
bash scripts/check.sh m1
```

`scripts/check.sh`는 버전 확인, `--headless --path . --import`, suite 실행을 순차 수행합니다.
M0 suite는 화면 scene 로드·생명주기 어댑터 검사, M1 suite는 콘텐츠·규칙·경로·결정론 검사를 포함합니다.
GDScript 파싱 오류가 exit 0으로 끝나는 경우도 막도록 엔진 오류 로그와 필수 완료 표지를 함께 검사합니다.
CI에서도 같은 wrapper를 실행하며 실패 프로브로 잘못된 fixture와 빈 suite를 각각 거부하는지 먼저 확인합니다.

직접 suite 실행 계약은 다음과 같습니다.

```bash
"$GODOT_BIN" --headless --path . --script tests/run_tests.gd -- --suite m0
"$GODOT_BIN" --headless --path . --script tests/run_tests.gd -- --suite m1
```

export preset 이름은 `Android`와 `iOS`로 고정합니다.
M0 작업에서 출력 디렉터리와 preset을 준비한 뒤 다음 명령을 사용합니다.

```bash
"$GODOT_BIN" --headless --path . --export-debug Android build/android/chef-al-mando.apk
"$GODOT_BIN" --headless --path . --export-debug iOS build/ios/chef_al_mando.xcodeproj
```

Android는 기본 debug APK 경로로 시작합니다.
iOS는 export된 Xcode 프로젝트의 실제 scheme을 `xcodebuild -list`로 확인한 뒤 개인 개발 서명으로 빌드합니다.
실제 scheme·Team ID·기기 OS가 아직 미확정이므로 서명·설치 명령은 M0 실행 기록에 최종 값을 적습니다.
export 성공만으로 설치·실기기 실행 통과를 주장하지 않습니다.
`build/`, `.godot/`, 서명 파일은 추적하지 않고 생성된 Xcode 프로젝트를 직접 고치지 않습니다.

## 8. 근거와 남은 결정

Oracle의 개인 프로젝트 `chef-al-mando` 조회에서 예약·소비와 모바일 배포에 적용할 선례는 `[no precedent found]`였습니다.
따라서 이 명세는 확정 블루프린트와 현재 저장소를 근거로 첫 구현 계약을 제안합니다.

- 로컬 `Godot --version`, `--help`: 엔진 버전, headless·script·export 옵션을 확인했습니다.
- [공식 Android export 문서](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html): JDK와 Android SDK 설정을 M0 환경 검사에 포함합니다.
- [공식 iOS export 문서](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_ios.html): macOS·Xcode·템플릿과 Team ID·Bundle ID가 필요하므로 서명 확인을 M0에 둡니다.
- [공식 CLI 문서](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html): headless 테스트와 preset 기반 export 명령의 참고 자료입니다.

공식 stable 문서는 이동하는 링크이므로 템플릿 확보 시 선택 버전의 요구사항을 다시 대조합니다.
Android 기종과 OS는 구매 후 확정하고, 서명 자격과 템플릿 가용성은 M0 선행 점검에서 확인합니다.
