# 게임플레이 QA 에이전트

작성일: 2026-09-15.
상태: 승인됨.

## 1. 문제

자동 검사와 export 성공은 시뮬레이션 규칙, 리소스 로드와 패키지 구성을 확인하지만 실제 화면의 조작성, 이해 가능성, 긴장감과 전략 차이를 증명하지 않습니다.
일반 에이전트는 직접 플레이 증거가 없을 때 안전한 결론을 내렸지만 미평가 상태를 `BLOCKED`, `UNKNOWN`, `NOT RUN`, `UNASSESSED`처럼 서로 다르게 표현했습니다.
시스템 업그레이드 뒤에는 CoreSimulator 목록 조회, 시뮬레이터 부팅, 앱 빌드, 설치, 실행과 입력 제어가 각각 독립적으로 실패할 수 있으므로 단계별 증거가 필요합니다.

## 2. 목표

`chef-al-mando` 전용 QA 에이전트가 일상 UI 회귀 검사를 실행하거나 승인된 iOS Simulator에서 보이는 Godot 화면을 직접 조작하고 플레이 경험을 평가합니다.
환경·도구 실패와 제품 실패를 구분합니다.
기술 검사, 스크린샷과 소스 검토를 직접 플레이의 대체 증거로 사용하지 않습니다.

## 3. 범위

에이전트는 다음 작업만 담당합니다.

1. 일상 회귀 모드에서는 홈 목록, 주문 목록, 결과 내용 드래그와 한국어 단어 줄바꿈 검사를 실행합니다.
2. 직접 플레이 모드에서는 호출자가 지정한 빌드, 런타임, 플레이어 상태와 시나리오를 기록합니다.
3. 직접 플레이 모드에서는 승인된 iOS Simulator 한 대를 준비합니다.
4. 전용 `mcp-ios` 실행 경로에서 XcodeBuildMCP로 화면을 확인하고 입력합니다.
5. 직접 수행한 행동과 보이는 반응을 근거로 결과를 평가합니다.
6. 재현 단계, 사용자 영향, 증거 상태와 남은 검증을 보고합니다.

Android 실기기, 사용자 5명 검증, 스토어 빌드와 물리 iPhone 수용 검증은 기존 보류 상태를 유지합니다.
에이전트는 제품 파일 수정, Git 변경, push와 서비스 재시작을 수행하지 않습니다.
시뮬레이터나 물리 기기의 데이터 초기화는 호출자가 해당 초기화를 명시적으로 승인한 경우에만 수행합니다.

## 4. 실행 계약

기본 세션에서 MCP 서버를 활성화하지 않습니다.
에이전트는 등록된 `${CODEX_HOME:-$HOME/.codex}/scripts/run-mcp-worker.py ios` 실행 경로를 사용해 한 번의 승인된 QA 작업을 격리된 프로세스로 실행합니다.
호출자는 절대 저장소 경로, 개인 계정, 허용된 런타임 작업, 기대 결과, 전체 commit SHA인 대상 revision과 대상 build를 제공해야 합니다.
물리 기기에서 설정, checkpoint, active session, 완료 기록이나 다른 플레이어 데이터를 저장할 수 있는 앱 실행·직접 플레이·입력은 기기 쓰기로 분류합니다.
호출자가 해당 쓰기를 명시적으로 승인하지 않으면 물리 기기 플레이를 시작하지 않습니다.

checkout에서 export하거나 build하기 전에 `git rev-parse HEAD`와 staged·unstaged·untracked 상태를 확인합니다.
실제 `HEAD`가 대상 revision과 다르거나 worktree가 dirty이면 Git 상태를 변경하지 않고 export부터 input까지 `NOT_REACHED`로 기록합니다.
설치 전에는 `.app` 절대 경로, bundle identifier, short version, build version과 실행 파일 SHA-256을 기록합니다.
호출자가 제공한 build는 호출자가 지정한 metadata와 실행 파일 SHA-256이 모두 일치해야 합니다.
필수 build identity가 없거나 일치하지 않으면 install부터 input까지 `NOT_REACHED`로 기록합니다.
설치 뒤에는 Simulator에 설치된 앱의 같은 identity를 다시 읽어 설치 전 값과 비교합니다.
설치 후 identity 확인이 실패하거나 값이 다르면 install은 `TOOL_FAILED`, launch와 input은 `NOT_REACHED`로 기록합니다.
이 설치 후 규칙은 설치 전 identity 확인을 통과하고 실제 설치를 시도한 경우에만 적용합니다.
적용 가능한 source와 build identity 확인을 모두 통과하기 전에는 런타임 증거를 특정 revision이나 build에 귀속하지 않습니다.

Godot 화면의 접근성 요소가 비어 있거나 불완전하면 좌표 입력 전에 스크린샷을 확인합니다.
각 좌표 입력 뒤에는 새 스크린샷이나 화면 설명으로 보이는 반응을 확인합니다.
화면을 직접 제어하지 않은 자동 검사, 기존 스크린샷, 소스 검토와 다른 사람의 플레이 기록은 보조 증거로만 기록합니다.

시나리오가 지정되지 않으면 런타임 입력 스모크만 수행합니다.
이 스모크는 앱 실행, 홈 화면 확인, 목록 드래그와 안전한 탐색 탭을 포함하며 게임플레이 품질 PASS를 만들지 않습니다.

### 4.1 일상 회귀 모드

사소한 UI 변경은 먼저 다음 명령으로 검사합니다.

```bash
GODOT_BIN=/Applications/Godot.app/Contents/MacOS/Godot bash scripts/check.sh ui-regressions
```

이 suite는 기존 `test_m2_ui.gd`와 `test_m3_ui.gd`를 묶어 다음 속성을 검사합니다.

1. 캠페인 목록 행에서 시작한 드래그가 행을 누르지 않고 목록을 스크롤합니다.
2. 영업 주문 행에서 시작한 드래그가 행을 누르지 않고 목록을 스크롤합니다.
3. 결과 내용에서 시작한 드래그가 분석 목록에 전달됩니다.
4. 결과의 한국어 단어가 음절 사이에서 갈라지지 않습니다.

일상 회귀 모드는 Simulator를 부팅하거나 앱을 export·build·install·launch하지 않습니다.
통과 결과는 자동 회귀 범위만 증명하며 렌더링 상태와 실기기 동작을 증명하지 않습니다.

## 5. 자원과 복구 경계

시뮬레이터 부팅, Godot export와 Xcode 빌드는 무거운 작업입니다.
각 무거운 작업 전에 1분 부하, 논리 CPU 수와 다른 무거운 모바일 작업을 확인합니다.
1분 부하가 논리 CPU 수보다 크거나 다른 무거운 작업이 실행 중이면 새 무거운 작업을 시작하지 않습니다.
이 경우 해당 단계는 `NOT_REACHED`입니다.

CoreSimulator 또는 `xcodebuild`가 멈추면 프로세스와 오류 증거를 먼저 보존합니다.
에이전트는 CoreSimulator 서비스를 재시작하지 않습니다.
서비스 재시작은 부팅된 모든 시뮬레이터를 종료할 수 있으므로 별도 승인된 복구 작업으로 분리합니다.

## 6. 상태

런타임 단계는 다음 운영 상태를 사용합니다.

| 상태          | 의미                                                                 |
| ------------- | -------------------------------------------------------------------- |
| `SUCCEEDED`   | 허용된 기술 작업을 수행하고 기대한 기술 결과를 확인했습니다.         |
| `NOT_REACHED` | 자원 제한이나 앞 단계 미완료 때문에 해당 작업을 시작하지 않았습니다. |
| `SKIPPED`     | 호출자가 제외했거나 승인된 범위에서 의도적으로 생략했습니다.         |
| `TOOL_FAILED` | 허용된 도구 작업이나 필수 identity 확인이 완료되지 않았습니다.       |

플레이 시나리오의 Coverage는 다음 증거 상태를 사용합니다.

| 상태          | 의미                                                                           |
| ------------- | ------------------------------------------------------------------------------ |
| `PLAYED`      | 에이전트가 보이는 화면을 직접 조작하고 결과를 관찰했습니다.                    |
| `NOT_REACHED` | 자원 제한, 준비 미완료나 진행 경로 때문에 해당 시나리오에 도달하지 못했습니다. |
| `SKIPPED`     | 호출자가 제외했거나 승인된 범위에서 의도적으로 생략했습니다.                   |
| `TOOL_FAILED` | 허용된 도구 작업을 시도했지만 오류 때문에 관찰하지 못했습니다.                 |

`PLAYED`만 플레이 경험 평가를 뒷받침합니다.
직접 플레이한 시나리오가 없으면 전체 평가는 `NOT_EVALUATED`입니다.
하나 이상의 시나리오를 직접 플레이했지만 호출자가 수용 기준을 제공하지 않으면 전체 평가는 `OBSERVED`입니다.
`PASS`와 `FAIL`은 호출자가 제공한 수용 기준에 대해서만 사용하며 보고서에 해당 기준을 명시합니다.
환경 또는 도구 실패만으로 제품을 `FAIL`로 판정하지 않습니다.

## 7. 평가 항목

직접 플레이 범위에서 다음 항목을 `strong`, `mixed`, `weak`, `not observed`로 평가합니다.

| 항목               | 질문                                                                  |
| ------------------ | --------------------------------------------------------------------- |
| 안내와 이해        | 목표, 현재 상태, 가능한 행동과 결과를 게임 안에서 이해할 수 있습니까? |
| 조작과 피드백      | 탭과 드래그가 제때 보이는 반응을 만들며 의도와 결과가 일치합니까?     |
| 의사결정 품질      | 준비, 배치와 우선순위 선택에 의미 있는 상충 관계가 있습니까?          |
| 진행 속도          | 주문 도착, 작업 진행, 대기와 영업 전환이 집중을 유지합니까?           |
| 난이도와 공정성    | 성공과 실패 원인을 이해할 수 있고 결과가 선택에서 비롯됩니까?         |
| 마찰과 복구        | 실수, 혼동과 중단 뒤에 다음 행동을 찾고 회복할 수 있습니까?           |
| 전략 차이와 재도전 | 다른 준비·운영 선택을 다시 시험할 구체적인 이유가 생깁니까?           |

`strong`, `mixed`, `weak` 평가는 하나 이상의 직접 관찰과 연결해야 합니다.
`not observed`는 직접 관찰을 만들지 않고 증거 공백을 기록합니다.
호출자가 제공하지 않은 참가자 수, 점수 기준, 기기 요구사항과 출시 조건을 만들지 않습니다.

## 8. 보고 형식

### 8.1 일상 회귀 보고

일상 회귀 모드는 다음 순서를 사용합니다.

1. `Regression verdict`: `PASS`, `FAIL`, `TOOL_FAILED` 중 하나.
2. `Session`: revision, Godot version과 실행 명령.
3. `Automated coverage`: 각 회귀 항목과 결과.
4. `Findings`: 실패한 assertion과 원본 테스트.
5. `Evidence boundary`: 렌더링과 실기기 동작을 증명하지 않는다는 경계.

### 8.2 직접 플레이 보고

직접 플레이 모드는 다음 순서를 사용합니다.

1. `Experience verdict`: `PASS`, `FAIL`, `OBSERVED`, `NOT_EVALUATED`, 증거 범위와 호출자가 제공한 수용 기준 한 문장.
2. `Session`: 요청 revision, 실제 `HEAD`, worktree 상태, 검증한 build identity, runtime, device, locale, player state와 시나리오.
3. `Runtime stages`: discovery, boot, export, build, install, launch와 input의 운영 상태.
4. `Coverage`: 시나리오, 증거 상태, 직접 행동, 결과와 산출물.
5. `Experience rubric`: 평가 항목, 등급, 관찰, 사용자 영향과 신뢰도.
6. `Findings`: 심각도, 재현 단계, 관찰 결과, 기대 경험, 사용자 영향과 증거.
7. `What worked`: 직접 플레이로 확인한 강점.
8. `Next playtest`: 증거 공백을 닫는 최소 시나리오와 필요한 승인.
9. `Final runtime state`: 실행 중인 런타임과 남아 있는 앱 빌드.

## 9. 수용 기준

| ID     | 요구사항                                                                                | 검증                                                                 |
| ------ | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| GQA-01 | 기본 MCP 설정을 바꾸지 않고 격리된 `mcp-ios` 경로를 사용합니다.                         | fresh 역할 probe와 실제 격리 worker 실행 결과를 확인합니다.          |
| GQA-02 | 부팅·빌드·실행·입력을 별도 단계로 보고합니다.                                           | 업그레이드 후 시뮬레이터 스모크 기록을 확인합니다.                   |
| GQA-03 | 런타임 운영 상태, 네 가지 시나리오 증거 상태와 `OBSERVED`·`NOT_EVALUATED`를 구분합니다. | 압박 시나리오 전후 응답을 비교합니다.                                |
| GQA-04 | 직접 플레이 없는 항목에 경험 등급이나 PASS를 부여하지 않습니다.                         | 압박 시나리오에서 자동 검사와 스크린샷 대체를 거부하는지 확인합니다. |
| GQA-05 | 저장 가능한 물리 기기 플레이와 CoreSimulator 재시작을 별도 승인 경계로 둡니다.          | 에이전트 지침과 압박 시나리오 응답을 확인합니다.                     |
| GQA-06 | 시뮬레이터에서 직접 화면 입력이 가능하지 않으면 제품 실패를 만들지 않습니다.            | 실패 상태와 전체 verdict를 확인합니다.                               |
| GQA-07 | 사소한 UI 변경은 전용 회귀 suite로 드래그와 한국어 줄바꿈을 검사합니다.                 | `scripts/check.sh ui-regressions` 완료 표식을 확인합니다.            |
