# 압력 영업 재조율 명세

작성일: 2026-09-21.
상태: 2026-09-21 운영자가 설계 세션에서 게이트 규칙, 조율 수단, 정책 형태, 목표 방향과 아래 설계를 승인했습니다.
이 명세는 [수요 예보·미장·리뷰 명세](mise-forecast-reviews.md) §4·§10과 [캠페인 운영 압력 검증](../notes/kitchen-pressure-verification.md)의 2026-09-11 조율 규칙을 바꾸며, [M3 캠페인 명세](m3-campaign.md) §3의 "영업 수·공정·자원 상한 불변"은 유지합니다.

## 1. 문제

계획 3(`../plans/forecast-content-implementation.md`)은 두 가지를 측정했습니다.

- 후반 여섯 압력 영업은 2026-09-11 규칙 "기준 정책 여분 ≤ 제공 1건·손익 2,000"으로 목표 여분 1건 이내에 맞춰져 있어, 시드 추첨이 주문 구성을 ±1건만 바꿔도 시드 0 기준 정책이 목표를 놓칩니다.
  시작 폭 `max(1, 기준 건수 / 5)`에서 시도 30행 가운데 24행이 실패했고, `hot_queue` 시도 2는 프렙 조합 104가지 전부에서 우선순위 유무와 무관하게(작성 발주·배치 기준) 통과가 없었습니다.
  그래서 `forecast_slack`은 비어 있고 플레이어에게 보이는 변동은 아직 없습니다.
- 두 영업은 자기 지렛대 없이도 통과합니다.
  `split_duties`는 담당 없이 노동량 1짜리 미장 한 개만 준비해도 최대치(26건·12,350원)라 어떤 목표나 `prep_labor_capacity`로도 담당 유무를 가르지 못하고, `final_service` 기준 정책은 구이 우선순위 지렛대를 잃은 채 프렙만으로 통과하는 조합이 하나뿐입니다.
  지금의 3전략 게이트는 지렛대를 바꾸면 결과가 달라지는지만 보므로 이 구멍을 잡지 못합니다.

두 문제의 뿌리는 같습니다.
영업이 정확히 목표에 맞춰져 있으면 변동을 흡수할 수 없고, 지렛대가 필요한지는 아무 게이트도 묻지 않습니다.

## 2. 목표

1. 여섯 압력 영업(`hot_queue`부터 `final_service`까지)이 시드 0과 시도 1~5의 추첨에서 모두 풀리고 무계획은 모두 미달하도록 여유를 갖습니다.
2. 영업마다 자기 운영 문제의 지렛대가 실제로 필요합니다.
3. 그 위에서 `forecast_slack`을 작성해 두 번째 시작부터 주문 구성이 달라집니다.

재미·난이도의 판정은 이 명세의 검사가 아니라 [플레이테스트 명세](playtest-price-validation.md)가 맡습니다.
검사는 "풀리는가"와 "지렛대가 필요한가"만 답합니다.

## 3. 접근

승인한 접근은 **여유 우선**입니다.
영업마다 노동량·예산·발주 여유를 먼저 주고, 그 여유로 무계획까지 통과하면 목표를 올려 되돌립니다.
지렛대 자체가 불필요한 영업은 자원으로 고칠 수 없으므로 주문 구성·도착 tick을 바꿔 지렛대가 필요해지게 재설계합니다.

검토 뒤 채택하지 않은 안:

- 구성 우선(자원은 두고 구성만 바꿈): 영업의 정체성이 크게 바뀌고, 여유 없이는 시드 변동을 여전히 흡수하지 못합니다.
- 미세 slack(냉식 메뉴끼리만 교환): 화구 부하가 바뀌지 않아 플레이어에게 변동이 보이지 않습니다.
- 시드별 정책: 콘텐츠는 덜 바꾸지만 시뮬레이션이 바뀔 때마다 최대 30개 정책을 다시 맞춰야 하고, 실제 추첨을 모르는 플레이어의 경험을 대변하지 않습니다.

## 4. 게이트 계약

이 절이 2026-09-11 규칙을 대체합니다.
`check.sh m3`와 `check.sh mise`가 아래를 검사하며, 검사 통과는 재미 판정이 아닙니다.

### 4.1 시드 0 (3전략 게이트)

- 기준 정책은 두 목표를 통과하되 여분이 **제공 2건·손익 3,000 이하**입니다.
- 대체 정책 둘은 두 목표를 통과하고, 세 정책의 최종 상태 해시는 쌍별로 다릅니다.
- 무계획(발주·프렙·배치·담당·우선순위 모두 초기값)은 제공 2건 이상 또는 손익 1,500 이상 미달합니다.
- 기준 정책은 여덟 영업 모두에서 1배속과 4배속의 최종 상태 해시가 같습니다.

### 4.2 시도 1~5 (시드 게이트)

- 시도 인덱스 1~5의 시드마다 추첨 인지 기준 정책이 두 목표를 통과합니다.
  추첨 인지 기준 정책은 시드 0 기준 정책에 원재료별 `max(작성 발주, 추첨된 구성의 필요량)`을 발주로 맞춘 것이며, 발주가 예산을 넘어 거부되면 그 시도는 실패입니다.
- 같은 시드마다 무계획은 §4.1과 같은 폭(제공 2건 이상 또는 손익 1,500 이상)으로 미달합니다.
  계획 3의 게이트는 "미달"만 요구했으므로 이 항목은 강화입니다.
- 정책은 시드마다 하나입니다.
  시드별 정책은 두지 않습니다.

### 4.3 지렛대 필요성 (신설)

영업은 자기 지렛대를 데이터로 명시합니다.

| 영업            | 운영 문제        | 지렛대                                |
| --------------- | ---------------- | ------------------------------------- |
| `hot_queue`     | 온식 우선순위    | 메뉴 우선순위                         |
| `shared_stock`  | 공동 재고와 발주 | 발주(`set_purchase`)                  |
| `long_route`    | 설비 동선        | 배치(`move_station`·`rotate_station`) |
| `split_duties`  | 담당 분리        | 담당(`set_duty`)                      |
| `rush_hour`     | 주문 유입과 프렙 | 프렙(`set_prep`)과 우선순위           |
| `final_service` | 전체 운영 조합   | 없음(무계획 미달이 곧 지렛대 필요성)  |

- 무지렛대 정책은 기준 정책에서 그 영업의 지렛대에 속한 명령만 뺀 것입니다.
  `rush_hour`처럼 지렛대가 둘이면 둘 다 뺍니다.
- 무지렛대 정책은 시드 0에서 두 목표 가운데 하나 이상에 미달해야 합니다.
  미달 폭은 요구하지 않습니다.
- 지렛대는 `tests/fixtures/m3_policies.gd`가 영업 ID별 명령 종류 목록으로 소유합니다.
  시나리오 `.tres`의 `operation_problem`은 표시용 문구이며 게이트가 읽지 않습니다.

### 4.4 `forecast_slack`

- `first_shift`·`lunch_prep`은 0입니다.
- `hot_queue`부터는 메뉴별 `max(1, 기준 건수 / 5)`에서 시작합니다.
- 어떤 영업이 §4.1~§4.3을 통과하지 못하면 먼저 §5의 수단으로 여유를 만들고, 수단을 다 쓴 뒤에만 그 영업의 slack을 줄입니다.
- 한 영업의 slack을 전부 0으로 줄이는 것은 허용하지 않습니다.
  그 지경이면 그 영업은 §5의 재설계 대상입니다.
- 이동이 하나도 불가능한 slack(한 메뉴에만 폭이 있고 다른 메뉴는 모두 경계)은 변동을 만들지 않으므로 작성하지 않습니다.

## 5. 조율 수단과 불변

바꿀 수 있는 값과 순서:

1. 여유: `prep_labor_capacity`, `starting_budget`, 작성 `purchases`.
2. 목표: `minimum_served`·`minimum_profit`은 올리기만 합니다.
   무계획이 §4.1의 미달 폭을 잃을 때 씁니다.
3. 구성: `order_recipe_ids`, `order_arrival_ticks`(또는 `first_arrival_tick`·`arrival_interval_ticks`), `order_count`.
   §4.3을 여유·목표로 만족시키지 못하는 영업에만 씁니다.
   파동 묶음과 150 tick 이상의 회복 구간, 메뉴 8종·재료 정의 12종 이내는 유지합니다.

바꾸지 않는 것:

- 설비 수·직원 수·격자, 레시피(재료·공정·시간·매출·인내), 미장 항목, 저장 스키마.
- 시드 0 항등, 자리바꿈 생성기, 결정론 계약(§9 of `mise-forecast-reviews.md`).
- 목표를 낮추는 것.

영업별 출발점(수치는 계획이 스윕으로 정하고 이 표는 방향만 말합니다):

| 영업            | 현재 증상                                          | 첫 수단                                               |
| --------------- | -------------------------------------------------- | ----------------------------------------------------- |
| `hot_queue`     | 수프 5건 전부 만료 채 12건·4,750원 정확히 통과     | 노동량·예산 여유 뒤 목표 상향                         |
| `shared_stock`  | 시도 1~5 가운데 1개만 통과                         | 예산·발주 여유                                        |
| `long_route`    | 시도 1~5 가운데 2개 통과                           | 노동량 여유                                           |
| `split_duties`  | 담당 없이 미장 1개로 최대치                        | 구성 재설계(냉식·온식 동시 파동)와 목표 상향          |
| `rush_hour`     | 시도 1~5 가운데 1개 통과                           | 노동량 여유                                           |
| `final_service` | 프렙만으로 통과하는 조합 1개, 우선순위 지렛대 없음 | `prep_labor_capacity` 18 → 19~21(측정된 경계) 뒤 목표 |

## 6. 도구와 방법

- `tests/sweep_policies.gd`에 두 옵션을 더합니다.
  `--purchases draw`는 `draw_aware_policy`와 같은 발주를 고정하고, `--without <종류,…>`는 기준 정책에서 지렛대 명령 종류를 빼서 무지렛대 정책을 돌립니다.
  스윕이 게이트와 같은 정책 형태를 실행해야 스윕 결과가 게이트 통과를 예측합니다.
- 영업마다 "여유 → 목표 → 구성" 순서로 값을 정하고, 각 단계의 스윕 인자·조합 수·통과 수·최고를 `docs/notes/kitchen-pressure-verification.md`에 새 절로 남깁니다.
  권위는 커밋된 `.tres`와 `m3_policies.gd`에 있습니다.
- 값이 바뀐 영업은 기준·대체 정책을 다시 맞출 수 있습니다.
  정책 재조정만으로 §4를 통과시키려 하지 않습니다.

## 7. 저장과 버전

- `forecast_slack`을 작성하는 커밋은 콘텐츠 버전을 7로 올립니다.
  시드가 있는 세션의 일정이 스냅샷과 달라지므로 버전 6 이하의 진행 중 영업은 모든 시나리오에서 재시작하고 완료·최고 기록과 준비 기본값은 보존합니다.
- 목표가 올라간 영업의 완료 기록은 그대로 두며, `legacy_completed` 표식 규칙은 콘텐츠 버전 1의 것이라 적용하지 않습니다.
  최고 기록은 `maximum_profit`(예보 상한 기준)이 커지므로 계속 유효합니다.
- 스키마는 4 그대로이고 `sim_version`은 건드리지 않습니다.

## 10. 구현 순서

각 단계에서 기존 검사가 계속 통과해야 합니다.

1. 게이트: 지렛대 목록과 무지렛대 검사, §4.1 여분 규칙, §4.2 미달 폭 강화, 스윕 도구의 두 옵션.
   지렛대 검사는 `split_duties`에서 실패하는 상태로 커밋하지 않고, 같은 계획의 재조율 Task가 통과시킨 뒤 함께 커밋합니다.
2. 재조율: 영업별로 여유 → 목표 → 구성 순서로 값을 정하고 정책을 다시 맞춥니다.
   `split_duties`·`final_service`부터 시작합니다(측정된 증상이 가장 명확함).
3. slack 작성과 콘텐츠 버전 7, 두 PCK 검사.
4. 문서: §9의 변경과 검증 기록.

세부 작업 분할과 파일 경로는 구현 계획이 정합니다.

## 11. 선례

- 계획 2a·2b의 시드 0 재조정(2026-09-20·21)은 정책만 바꾸는 방식의 한계를 보였고, 계획 3의 측정이 이 명세의 §1을 만들었습니다.
- 2026-09-11 압력 검증 기록의 여분 규칙은 스테이지를 빡빡하게 유지하려는 의도였으며, 이 명세는 그 의도를 §4.3(지렛대 필요성)으로 옮기고 여분은 변동 흡수에 씁니다.
- 개인 계정에서 "시드 변동을 흡수하는 콘텐츠 여유"에 직접 해당하는 선례는 `[no precedent found]`입니다.
