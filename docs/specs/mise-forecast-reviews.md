# 수요 예보·미장 비대칭·고객 리뷰 명세

작성일: 2026-09-19.
상태: 2026-09-19 운영자가 설계 세션에서 접근안 A와 세 묶음의 설계를 승인했습니다.
이 명세는 [블루프린트](../plans/PLAN.md)의 "고정 주문 일정" 방향을 바꾸는 변경을 포함하며, 그 변경은 같은 날 §10.1에 기록했습니다.

## 1. 문제

2026-09-18의 검토에서 두 결함을 확정했습니다.

- 정체성: 시뮬레이션은 설비 역할 4종(`storage`·`cold`·`hot`·`pass`), 같은 4단계 선형 공정, 격자 이동, 우선순위, 마감으로 이루어진 범용 스케줄러입니다.
  `sim/` 전체에 주방에서만 성립하는 규칙이 없고, 재료와 작업대의 이름만 바꾸면 어떤 산업에도 붙습니다.
- 분량: 8개 영업 × 300초로 영업 시간 합계가 1배속 40분이고, 주문 일정이 완전히 고정이라 한 번 푼 시나리오는 재플레이 변동이 없습니다.
  [경쟁작 가격 앵커](../notes/competitor-price-anchors.md)에서 최고 기록 이외의 재플레이 표면은 선불 경영 게임의 입장권으로 확인됐습니다.

운영자는 세 가지를 추가로 지적했습니다.
직원 숙련도가 없고, 메뉴별 공정·동선·재료 구성이 코드 속에만 있어 플레이어는 "가까이 두면 빨리 나간다" 수준으로만 읽으며, 손님 인내 시간은 배정 정렬 로직만 알고 있습니다.

## 2. 목표와 선택한 규칙

운영자는 주방 고유 규칙으로 **미장플라스**를 선택했습니다.
요리사의 감으로 재료를 적정량 준비하고, 어떤 미장은 여러 메뉴가 나눠 쓰니 넉넉해도 되지만 어떤 미장은 한 메뉴만 쓰고 비싸서 남으면 그대로 손실이 되는 비대칭이 핵심입니다.
이 규칙은 "역할명을 공장으로 바꿔도 성립하는가"라는 반증 기준을 통과합니다.

미장이 판단이 되려면 수요가 불확실해야 하므로 주문 구성을 예보와 시드로 바꿉니다.
미장 규칙이 다시 코드 속 숫자로 남지 않도록 마감 피드백을 고객 리뷰로 바꿉니다.
세 요소는 "미장 판단 → 영업 → 리뷰 → 다음 미장 판단"이라는 하나의 루프입니다.

이번 명세의 범위는 다음 세 가지입니다.

1. 수요 예보와 시드 변동.
2. 재료 단위 미장과 부분 프렙.
3. 고객 리뷰 피드백과 규칙을 읽을 수 있는 화면.

후반 시나리오의 메뉴 넣고 빼기와 직원 숙련도는 이번 범위에 넣지 않습니다.
플레이테스트 결과를 본 뒤 별도 명세로 다룹니다.

## 3. 접근

승인한 접근은 **콘텐츠 계층 생성기**입니다.
시나리오는 도착 슬롯과 예보 범위만 정의하고, 순수 함수인 생성기가 `(시나리오, 시드)`에서 시뮬레이션이 지금 읽는 것과 같은 모양의 주문 배열을 만듭니다.
시뮬레이션의 도착 처리, 결정론 계약, 저장 형식은 그대로 두고 시드만 스냅샷에 더합니다.
시뮬레이션 내부 추첨과 손으로 쓴 일정 여러 벌은 검토 후 채택하지 않았습니다.

## 4. 수요 예보와 시드

### 4.1 데이터

- 시나리오는 기존 `order_recipe_ids`를 그대로 유지하며, 이것이 **시드 0의 기준 메뉴 순서**입니다.
  8개 시나리오 모두 이 배열을 가집니다.
- 도착 tick은 지금처럼 두 방식 중 하나입니다.
  `order_arrival_ticks` 배열이 있으면 그 값을, 없으면 `first_arrival_tick + arrival_interval_ticks × 순번`을 씁니다(`first_shift`, `lunch_prep`).
  생성기는 어느 방식이든 도착 tick을 바꾸지 않습니다.
- 시나리오에 `forecast_slack: Dictionary[String, int]`를 추가합니다.
  키는 판매 메뉴 ID, 값은 기준 건수에서 위아래로 허용하는 폭입니다.
  없는 메뉴는 폭 0으로 처리합니다.
- 메뉴별 예보 범위는 `[기준 건수 − slack, 기준 건수 + slack]`을 0 이상으로 자른 값이며, 손으로 따로 적지 않고 항상 계산합니다.
- 총 주문 수는 `order_count`로 고정입니다.
  파동 묶음과 150 tick 이상의 회복 구간 규칙은 생성기가 건드리지 않으므로 그대로 보장됩니다.
- **첫 두 영업의 slack은 0으로 둡니다(제안).**
  `first_shift`는 메뉴가 하나라 변동이 불가능하고, `lunch_prep`은 미장과 예보를 처음 배우는 영업이므로 예보가 실제와 같게 둡니다.
  변동은 `hot_queue`부터 시작하며, 이 경계는 [플레이테스트 명세](playtest-price-validation.md)의 튜토리얼 게이트 결과에 따라 옮길 수 있습니다.

### 4.2 생성기

`ScheduleGenerator`(`content/schedule_generator.gd`)는 `(scenario, seed) → PackedStringArray`의 순수 함수입니다.

1. 시드 0은 작성된 `order_recipe_ids`를 그대로 반환합니다.
2. 그 외 시드는 시드로 초기화한 `RandomNumberGenerator`로 메뉴별 건수를 정합니다.
   기준 건수에서 시작해, 한 메뉴에서 하나를 빼고 다른 메뉴에 하나를 더하는 이동을 반복하되 모든 메뉴가 예보 범위 안에 있어야 합니다.
   이동 횟수와 대상은 같은 RNG에서 뽑으며, 범위가 이동을 하나라도 허용하면 최소 한 번은 이동합니다.
3. 정해진 건수의 메뉴 목록을 같은 RNG로 섞어 슬롯 순서대로 배정합니다.

같은 시드는 같은 엔진·콘텐츠·시뮬레이션 버전에서 항상 같은 배열을 만듭니다.
생성기는 시뮬레이션 상태, 시계, 저장 파일을 읽지 않습니다.
모든 slack이 0인 시나리오는 어떤 시드에서도 기준 순서를 그대로 반환합니다.

기존 `Definitions.seed` 필드는 M1·M2 fixture의 메뉴 회전 오프셋이며 캠페인 시나리오의 `order_schedule()`은 이를 읽지 않습니다.
이 필드는 그대로 두고 영업 시드와 혼동하지 않도록 새 값은 `service_seed`로 부릅니다.

### 4.3 시드의 출처

- 캠페인 기록은 시나리오별 `attempt_index`를 가지며 초기값은 0입니다.
  캠페인 화면에서 영업을 새로 시작할 때 **현재 인덱스로 시드를 만든 뒤** 인덱스를 1 올립니다.
  인덱스 0의 시드는 0이고, 인덱스 1 이상의 시드는 `scenario_id`와 인덱스를 결합한 문자열의 안정적인 해시입니다.
  따라서 어떤 플레이어든 각 시나리오의 첫 플레이는 작성된 일정이고, slack이 있는 시나리오는 두 번째 시작부터 구성이 달라집니다.
  해시는 실행·플랫폼에 관계없이 같은 값이어야 하며, 고정 입력의 기대값을 검사로 고정합니다.
- **마감 화면의 재도전은 같은 시드를 다시 씁니다.**
  "실패하면 같은 조건으로 재도전"이라는 블루프린트 §2의 원칙은 유지됩니다.
- **캠페인 화면에서 다시 고르면 새 시드**이며 이것이 "다른 날"입니다.
- 이어하기는 스냅샷의 `service_seed`를 복원합니다.
- `attempt_index`가 없는 기존 기록은 0으로 복원하므로, 기존 플레이어도 갱신 뒤 첫 시작은 작성된 일정입니다.

### 4.4 브리핑

브리핑은 총 주문 수와 메뉴별 예보 범위를 보여 줍니다.
예: "주문 20건 예상: 단백질 구이 8–12, 곡물 수프 4–6, 채소 샐러드 4–6."
실제 구성은 영업이 시작될 때까지 보이지 않습니다.

## 5. 미장 비대칭

### 5.1 미장 항목

미장을 메뉴별 1:1 손질 재료에서 **재료 단위 항목**으로 바꿉니다.
아래 6종과 배정은 운영자가 승인한 제안이며, 구현 PR에서 현재 레시피의 재료 사전과 맞추고 시드 0 풀림 검사로 수량을 조정합니다.

| 미장        | 원재료     | 쓰는 메뉴 (제안)                                   | 성격                      |
| ----------- | ---------- | -------------------------------------------------- | ------------------------- |
| 손질 채소   | 채소       | 채소 샐러드, 곡물 샐러드, 버섯 샐러드, 단백질 덮밥 | 여러 메뉴가 나눠 씀, 저렴 |
| 손질 곡물   | 곡물       | 곡물 샐러드, 곡물 수프, 곡물 볶음, 단백질 덮밥     | 여러 메뉴가 나눠 씀, 저렴 |
| 손질 버섯   | 버섯       | 버섯 샐러드, 버섯 수프                             | 두 메뉴가 씀              |
| 해동 단백질 | 단백질     | 곡물 볶음, 단백질 덮밥                             | 두 메뉴가 씀, 비쌈        |
| 재운 단백질 | 단백질     | 단백질 구이                                        | 한 메뉴만 씀, 비쌈        |
| 수프 베이스 | 채소, 곡물 | 곡물 수프, 버섯 수프                               | 두 메뉴가 씀              |

- 미장 항목은 재료 정의에 두고 `labor_units`, 원가(구성 원재료 원가의 합), 만드는 데 소비하는 원재료를 가집니다.
- 레시피는 `prepared_ingredient_id` 하나 대신 필요한 미장 ID 집합을 참조하며, 집합은 비어 있을 수 없습니다.
  콘텐츠 검사는 존재하지 않는 미장 참조, 빈 집합, 어떤 판매 메뉴도 쓰지 않는 미장을 실패로 처리합니다.
- 비대칭은 별도 플래그가 아니라 **몇 개 메뉴가 쓰는가 × 원가**에서 나옵니다.
  영업 사이 이월 없음 규칙은 유지하므로 "다음날 못 쓴다"는 모든 미장에 해당하고, 차이는 어디에 걸었느냐에서 납니다.
- **표시 이름은 실제 식재료명을 씁니다.**
  `단백질`·`채소`·`곡물` 같은 분류명은 M1 자리표시 fixture에서 이어진 것이며 의도된 결정이 아닙니다.
  ID(`protein`, `vegetable`, `grain`, `mushroom`)와 시나리오 참조는 유지하고 `display_name`, `en.po` 번역, 메뉴 아이콘만 바꾸므로 저장 호환에 영향이 없습니다.
  실제 이름은 [구현 순서](#12-구현-순서)의 미장 콘텐츠 단계에서 운영자가 정하며, 블루프린트 §2의 "요리 지식이 없어도 첫 영업을 이해"라는 원칙에 맞춰 익숙한 재료를 고릅니다.
  분류명이 남아 있으면 "최고의 단백질 구이였어요" 같은 리뷰 문구가 사람 말로 읽히지 않으므로, 리뷰 문구 작성은 이름 확정 뒤에 합니다.

### 5.2 준비 단계

- `set_prep` 명령의 대상은 메뉴 ID에서 미장 ID로 바뀝니다.
- 준비 노동량은 항목별 `labor_units × 수량`으로 소비하며 시나리오의 `prep_labor_capacity` 상한은 유지합니다.
- 미장을 만들면 구성 원재료를 즉시 소비합니다.
  예산·노동량·재료 부족은 지금처럼 거부합니다.

### 5.3 영업 중 규칙

- 주문을 배정할 때 레시피의 미장이 **모두** 재고에 있으면 지금처럼 `prep` 단계를 건너뛰고 미장을 소비합니다.
- 하나라도 없으면 냉식대에서 `prep`을 수행합니다.
  소요 시간은 `레시피 prep 시간 × (부족 항목 수 / 전체 항목 수)`를 올림한 값입니다.
  부족한 항목은 원재료를, 있는 항목은 미장을 소비하며, 각 소비는 정확히 한 번입니다.
- 예약과 소비의 원자성, 취소 시 예약 해제와 소비 손실 처리는 기존 규칙을 따릅니다.
- 미장 재고가 0이 되는 순간 `prepared_stock_depleted` 이벤트를 항목 단위로 냅니다.

### 5.4 마감 회계

- 남은 미장은 지금처럼 원가로 폐기 비용에 들어갑니다.
- 마감 분석은 미장 항목별 **준비량·사용량·폐기량**과, 그 항목이 비어서 원재료 경로로 간 주문 수를 남깁니다.
  리뷰와 셰프 권고가 이 값을 읽습니다.

## 6. 고객 리뷰

### 6.1 단위와 결정론

- 리뷰 단위는 **같은 tick에 도착한 주문 묶음(테이블)** 입니다.
  혼자 온 손님은 주문 하나가 한 테이블입니다.
- 리뷰는 마감 스냅샷의 주문 결과와 영업 시드에서 결정론적으로 만듭니다.
  문구 변형은 `(시드, 테이블 순번)`의 해시로 고르므로 같은 시드의 재도전은 같은 손님이 같은 말투로 옵니다.
- 리뷰와 평점은 저장하지 않고 마감 스냅샷에서 다시 만듭니다.

### 6.2 부류와 별점

제공된 접시의 부류는 인내 시간 자체가 아니라 **여유 시간에 대한 비율**로 정합니다.
레시피의 최소 공정 시간은 미장이 모두 있을 때의 공정 합계(`prep` 제외, 이동 제외)이고, 여유 시간은 `인내 시간 − 최소 공정 시간`입니다.
접시의 지연은 `(제공 tick − 도착 tick) − 최소 공정 시간`이며, 부류는 지연을 여유 시간으로 나눈 비율로 정합니다.
예를 들어 단백질 구이는 인내 500 tick, 최소 공정 260 tick이므로 여유는 240 tick이고, 도착 뒤 404 tick 안에 나가면 칭찬입니다.
인내 시간을 그대로 쓰면 구이는 공정만으로 인내의 70%를 쓰므로 칭찬이 사실상 불가능해지기 때문입니다.

| 부류      | 조건                              | 별점 | 문구                              |
| --------- | --------------------------------- | ---- | --------------------------------- |
| 칭찬      | 지연이 여유 시간의 60% 이하       | 5    | 메뉴 이름을 부르는 칭찬           |
| 늦은 칭찬 | 60% 초과 80% 이하                 | 4    | 맛은 좋았지만 기다린 초를 말함    |
| 늦은 칭찬 | 80% 초과 100% 이하                | 3    | 같음, 더 강한 표현                |
| 못 받음   | 기한 초과, 작업이 시작된 적 없음  | 1    | 가장 오래 기다린 원인을 손님 말로 |
| 못 받음   | 기한 초과, 작업이 시작됐으나 미완 | 2    | 같음                              |
| 취소당함  | 플레이어 취소                     | 2    | 주문이 취소됐다는 말              |

- 콘텐츠 검사는 모든 판매 메뉴의 여유 시간이 양수인지 확인합니다.
- "못 받음"의 원인 문구는 대기 원인과 1:1입니다.
  재료 부족은 어느 미장이 비었는지까지 말합니다.
  담당 없음·담당 직원 작업 중·작업대 사용 중은 주방이 정신없어 보였다는 말로, 경로 없음은 요리사가 오지 못했다는 말로 옮깁니다.
- 테이블 별점은 접시 별점의 평균이고, 오늘의 평점은 전체 주문 별점의 평균입니다.
  소수 첫째 자리까지 표시합니다.
- 별점은 목표에 넣지 않습니다.
  목표는 제공 수와 손익 그대로이며, 평점은 영업 요약에 표시만 합니다.

### 6.3 표시 순서

1. 제공된 주문이 하나라도 있으면 첫 리뷰는 반드시 칭찬 문구입니다.
   칭찬 부류의 접시가 있으면 그중 첫 테이블을, 없으면 제공된 접시 중 지연 비율이 가장 낮은 접시의 테이블을 고르고, 그 접시에는 별점을 유지한 채 칭찬 문구를 씁니다.
   엉망인 날에도 칭찬 하나는 먼저 오게 하려는 규칙이며, 별점은 속이지 않습니다.
2. 다음은 매출 손실이 가장 큰 실패 테이블입니다.
3. 다음은 가장 잦은 실패 원인의 첫 테이블입니다.
4. 나머지는 도착순입니다.

같은 테이블이 여러 조건에 해당하면 한 번만 보입니다.
기본 6개를 보이고 "더 보기"로 전체를 폅니다.
상단에 오늘의 평점과 부류별 건수를 둡니다.

### 6.4 문구 콘텐츠

- 문구는 `content/campaign/reviews/` 리소스에 둡니다.
  메뉴별 칭찬 2~3종, 늦은 칭찬 공통 2종, 실패 원인별 2종, 취소 1종으로 시작합니다.
- 문구 안의 초·메뉴명·미장명은 자리표시자입니다.
- 한국어 원문과 `translations/en.po` 번역이라는 기존 방식을 따릅니다.
- 콘텐츠 검사는 판매 메뉴에 칭찬 문구가 없거나 대기 원인에 실패 문구가 없으면 실패로 처리합니다.

## 7. 화면

- **브리핑**: §4.4의 예보 범위와 메뉴별 손님 인내 시간(초).
- **준비 화면의 미장 목록**: 항목마다 이름, 쓰는 메뉴 수, 원가, 노동량, 수량 조절.
  어디에 걸면 안전하고 어디가 위험한지 준비 단계에서 보이게 합니다.
- **준비 화면의 메뉴 상세**: 메뉴를 고르면 필요한 미장, 공정 사슬과 단계별 초("창고 → 손질 60초 → 화구 200초 → 패스"), 손님 인내 시간을 읽을 수 있습니다.
  이것으로 손질 재료가 있어도 창고를 들르는지, 구이에 채소가 드는지가 화면에서 답해집니다.
- **마감 화면**: 위쪽 "손님 리뷰"(평점, 부류별 건수, 리뷰 목록), 아래쪽 기존 "셰프 분석".
  프렙 권고는 미장 항목별 준비·사용·폐기로 바꾸고 발주·우선순위 권고는 유지합니다.
- 영업 중 주문 목록의 "N초 남음"은 유지합니다.
- 휴대폰 접이식 상세, 태블릿 병렬 패널, 안전 영역, 큰 글자, 한국어 줄바꿈 규칙은 기존 계약을 따릅니다.

## 8. 저장과 버전

- **콘텐츠 버전 5.** 미장 구조, `forecast_slack`, 리뷰 리소스가 추가됩니다.
  버전 1~4의 완료·최고 기록은 보존하고 `legacy_completed` 표식 규칙은 유지합니다.
  진행 중 영업은 미장 재고 구조가 달라지므로 모든 시나리오에서 다시 시작합니다.
  메뉴별 기본 우선순위 같은 준비 기본값은 보존합니다.
- **저장 스키마 4.** 캠페인 기록에 시나리오별 `attempt_index`, 영업 스냅샷에 `service_seed`, 준비 선택의 `prep_quantities`는 미장 ID를 키로 씁니다.
  스키마 1~3은 읽기만으로 바꾸지 않고 다음 정상 저장에서 4로 갱신하며, 이전 실행 파일은 4를 미래 버전으로 보호합니다.
- `prng_state`는 계속 `null`이며 시뮬레이션 내부 추첨은 없습니다.
- 알 수 없는 미래 버전, 손상 파일, 원본 비변경의 기존 보호 동작은 유지합니다.

## 9. 결정론 계약

- `ScheduleGenerator`는 `(시나리오, 시드)`의 순수 함수이고 시드 0은 작성된 일정과 같습니다.
