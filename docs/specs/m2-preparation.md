상태: 2026-09-08 승인, 구현 중.

## 1. 목표와 승인 범위

같은 주문 조건에서 프렙, 설비 배치, 우선순위를 바꾸면 결과와 병목이 달라지는 작은 플레이테스트 빌드를 만듭니다.
제품 기준은 [블루프린트](../plans/PLAN.md)의 재료·프렙, 이동·공간, M2 통과 조건입니다.
기존 규칙과 환경은 [M0·M1 명세](m0-m1.md)를 유지합니다.

M1 PR #3의 검토 head는 `45090bf41e34b0beda2685293931d4b4abe34496`이며 머지 결과와 파일 트리가 같습니다.
운영자는 최종 소스 `a4517e1`의 iPhone 설치 후 정상 동작을 승인했습니다.
설치와 승인 근거는 [PR #3의 승인 기록](https://github.com/AndrewDongminYoo/chef-al-mando/pull/3#issuecomment-5572738174)에 있습니다.
이 승인은 개별 탭 횟수나 마감 수치를 새로 계측했다는 뜻은 아닙니다.

운영자의 다음 마일스톤 진행 요청은 Android 실기기 검증 보류를 유지한 M2 착수 승인으로 해석합니다.
M0·M1의 양 플랫폼 전체 수용 기준이 통과했다는 뜻은 아닙니다.
운영자는 2026-09-08 이 명세의 프렙·배치·집계 규칙을 승인했습니다.

5. 첫 사용자 5명의 행동으로 재미를 판단합니다. → 검증: M2-13의 관찰 기록.

## 2. 이번 PR의 경계

플레이 가능한 시나리오는 직원 2명, 설비 4개, 메뉴 3종, 주문 20건, 300초 영업 하나로 유지합니다.
발주 수량, 메뉴별 프렙 수량, 설비 위치·작업 방향, 초기 직원 담당을 준비 화면에서 조절합니다.
영업 중 주문 우선순위·취소·담당과 일시정지·배속은 기존 명령을 사용합니다.
마감에는 손익·제공률·폐기와 누적 대기·이동 시간을 표시합니다.

프렙은 아래의 고정 선형 공정으로 구현합니다.
별도 시뮬레이션 엔진이나 범용 생산 그래프를 만들지 않습니다.
새 패키지나 플러그인을 추가하지 않습니다.

캠페인 확장, 시나리오 선택, 중간 저장, 영업 사이 재고 이월, 새 언어, 태블릿 제품화, 브랜딩, 아트 생성 자동화는 포함하지 않습니다.
태블릿의 기존 병렬 패널 회귀는 유지하며 완전한 태블릿 수용 기준은 M4에 남깁니다.
네 번째 메뉴는 데이터 확장 검증용 fixture에서만 사용합니다.

## 4. 준비 상태와 확정

`sim/preparation_plan.gd`의 `RefCounted` 객체가 발주·프렙·배치·초기 담당을 소유합니다.
화면은 준비 명령을 제출하고 복사된 미리보기를 표시합니다.
공유 `Resource`를 직접 변경하지 않습니다.

준비 명령에는 `apply_tick: 0`과 증가하는 `sequence`를 붙입니다.
영업은 준비 중에 진행되지 않으며 서비스 명령의 sequence는 새 영업에서 시작합니다.
실패한 명령은 변경 직전의 선택과 sequence를 유지하고 이유를 반환합니다.

발주는 구매 가능한 원재료만 정수로 입력합니다.
구매 비용과 고정 인건비의 합이 시작 예산을 넘는 증량은 거부합니다.
프렙에는 원재료와 남은 준비 노동량이 모두 필요합니다.
준비 수량을 줄이면 확정 전 미리보기만 다시 계산하며 이미 확정한 영업의 재고를 되돌리지 않습니다.
발주를 줄여 선택한 프렙을 만들 수 없게 되는 변경은 거부하고 프렙 수량을 먼저 줄이도록 안내합니다.

일시적으로 판매할 수 없는 메뉴가 생기는 발주 감소는 미리보기에서 허용하되 이유를 표시하고 영업 시작을 막습니다.
영업 시작 시 각 메뉴를 원재료 또는 중간 재료로 최소 한 인분 만들 수 있어야 합니다.
원재료와 노동량은 프렙 선택 전체에 대해 합산하며 메뉴별 검사만으로 공동 재고를 중복 사용하지 않습니다.

영업 시작은 한 번의 확정 연산입니다.
예산·수량·참조·프렙·경로를 다시 검사하고 원재료를 차감한 뒤 중간 재료를 생성합니다.
실패하면 영업을 시작하지 않으며 부분 차감도 남기지 않습니다.
같은 시작 버튼 입력을 반복해도 프렙을 다시 소비하지 않습니다.
확정 결과는 시작 재고, 선택한 배치·담당, 구매 비용, 준비 선택의 복사본을 포함합니다.
영업 중 준비 명령은 거부합니다.

재도전은 마지막 준비 선택으로 새 구매 재고와 예산을 구성한 준비 화면으로 돌아갑니다.
이전 영업의 현금·손실·잔여 재고는 이월하지 않습니다.
별도의 `기본 준비로 초기화` 버튼으로 이 명세의 기본값을 복구할 수 있습니다.

## 5. 영업 중 중간 재료

M1 메뉴의 `pickup → cook → serve`는 유지합니다.
M2 메뉴는 `pickup → prep → cook → serve`를 사용합니다.
메뉴마다 중간 재료 ID와 프렙 노동량을 정적 데이터로 정의하며 공정 시간·역할은 `ProcessDef`에서 읽습니다.
이 동작을 메뉴 ID별 조건문으로 구현하지 않습니다.

콘텐츠 검증은 원재료·중간 재료의 ID 중복과 참조 누락, 중간 재료의 구매, 프렙 노동량 0 이하, 공정 시간 0 이하를 거부합니다.
M2 공정은 위의 네 단계와 역할을 정확히 따라야 하며 순환·건너뛴 공정·일치하지 않는 역할은 거부합니다.
중간 재료는 M2에서 메뉴 하나에만 연결하고 원재료만으로 생성합니다.
중간 재료를 다시 프렙하는 연결과 원재료 없는 프렙은 허용하지 않습니다.
M1의 기존 세 단계 검증을 느슨하게 만들어 M2를 수용하지 않습니다.

첫 배정에서 사용 가능한 중간 재료 한 개가 있으면 이를 먼저 예약합니다.
없으면 해당 메뉴의 원재료 한 인분 전체를 예약합니다.
이 선택과 직원·설비·작업 위치·경로 확보는 모두 성공하거나 모두 실패합니다.
배정 후 이동 중에는 재료 경로를 바꾸지 않습니다.

중간 재료 경로는 수거 공정 시작 시 예약한 중간 재료만 한 번 소비하고 `prep`을 건너뜁니다.
원재료 경로는 수거 시작 시 원재료를 한 번 소비합니다.
손질 완료 시 주문에 귀속된 중간 결과를 만들고 조리 시작 시 그 결과를 한 번 사용합니다.
영업 중 만든 중간 결과를 다른 주문의 공용 재고로 돌리지 않습니다.
직원이 바뀌면 기존 이동·인계 규칙에 따라 결과물이 있는 위치에 들러 가져옵니다.

수거 시작 전 취소·만료·경로 실패는 원재료 또는 중간 재료의 예약을 해제합니다.
수거 시작 후에는 소비한 재료를 복구하지 않습니다.
손질 완료 후에도 다음 공정 전에 취소하면 그 중간 결과는 폐기하며 원재료와 중간 재료의 손실을 중복 계산하지 않습니다.
동시에 한 개의 중간 재료를 기다리는 두 주문 중 하나만 배정될 수 있어야 합니다.

중간 재료의 원가는 해당 한 인분에 투입한 원재료 원가와 같습니다.
중간 재료는 발주할 수 없으며 프렙으로 원가가 새로 생기지 않습니다.
마감 폐기는 원재료 잔량, 미사용 중간 재료, 취소·미제공 주문이 소비한 원가를 겹치지 않게 더합니다.
손익은 기존과 같이 매출에서 구매 재료비와 고정 인건비를 한 번씩 뺍니다.
기한과 마감은 같은 tick의 손질·조리·제공 완료보다 먼저 처리합니다.

## 6. 설비 배치

설비를 선택한 뒤 상하좌우 한 칸 이동 버튼과 작업 방향 회전 버튼으로 배치합니다.
설비 종류·수량·직원 시작 위치·격자 크기는 바꾸지 않습니다.
드래그는 필수 조작이 아닙니다.

작업 위치는 설비의 상하좌우 이웃 한 칸이며 회전 순서는 위·오른쪽·아래·왼쪽입니다.
후보 배치에서 벽·주방 밖·다른 설비와 겹치는 설비 타일, 막힌 작업 위치, 직원 시작 위치를 막는 배치는 거부합니다.
모든 설비 작업 위치가 같은 연결 영역에 있고 직원이 그 영역에 접근할 수 있어야 합니다.
거부하면 이전 배치를 유지하며 거부 이유를 표시합니다.

서로 다른 설비의 작업 위치 공유는 기존 작업 위치 독점 규칙을 따릅니다.
통로 타일이나 직원끼리의 충돌 예약을 추가하지 않습니다.
확정한 배치로 정적 경로를 다시 구성하며 영업 중 배치 변경은 거부합니다.

## 7. 화면과 마감 원인

준비 화면은 중앙 주방을 유지하고 `발주·프렙`, `배치·담당`, `요약`을 탭으로 전환합니다.
예산과 구매 비용, 준비 노동량, 영업 시작 가능 여부를 항상 읽을 수 있게 합니다.
프렙 수량은 `−`와 `+`, 배치는 방향·회전 버튼으로 조절합니다.
준비 선택과 거부 이유는 색상 외에 문구로도 표시합니다.

영업 화면에는 원재료와 중간 재료를 구분하고 `손질` 공정 문구를 추가합니다.
시간 제어 위치와 기존 접이식 주문 상세를 유지합니다.

시뮬레이션은 각 주문의 대기 원인별 tick, 이동 tick, 작업 tick과 종료 tick을 누적합니다.
각 tick의 배정·이동 처리 후 종료하지 않은 주문의 현재 상태를 한 번 집계합니다.
도착 tick은 포함하고 종료 tick은 제외합니다.
일시정지와 영업 종료 뒤에는 증가하지 않습니다.
주문별 세 시간의 합은 `종료 tick − 도착 tick`과 같아야 합니다.

대기 원인 네 종류를 유지하고 `담당 없음` 안에서 실제 담당 부재와 담당 직원 작업 중을 구분합니다.
설비별 시간은 이동 중 예약을 포함하므로 `예약·사용 시간`으로 표시합니다.
여러 주문의 시간을 더한 값은 실제 영업 시간보다 클 수 있어 `주문별 누적 시간`으로 표시합니다.

마감은 손익·제공률·폐기, 대기 원인별 누적 시간, 이동 시간, 설비별 예약·사용 시간을 표시합니다.
`가장 긴 대기`는 측정값의 최대 항목이며 손실의 유일한 원인이라고 단정하지 않습니다.
동률은 재료 부족·담당 없음·작업대 사용 중·경로 없음 순서로 표시합니다.
수치와 함께 `준비 다시 하기` 버튼을 제공합니다.

## 8. 대표 아트와 데이터 제작성

작은 탑다운 화면에 맞춘 직원 몸체 1개, 설비 4종, 메뉴 아이콘 3종을 적용합니다.
직원은 몸체를 재사용하고 색상·번호로 구분합니다.
이동 방향과 작업 상태 표현은 프레젠테이션에서만 적용합니다.
아이소메트릭이나 메뉴별 긴 애니메이션은 도입하지 않습니다.

대표 세트는 프로젝트에서 직접 작성한 SVG 원본으로 시작합니다.
각 아트의 작성·수정·화면 검수에 걸린 시간을 구분해 기록하며 에이전트 작업 시간을 사람의 제작 시간으로 일반화하지 않습니다.
작은 실제 표시 크기에서 외곽 잘림, 설비 앞뒤, 직원 접지점, 아이콘과 글자의 겹침을 확인합니다.
외부 소재가 필요해지면 사용 전에 출처와 상업 사용 권한을 기록합니다.
출처와 측정 결과는 `docs/notes/m2-production.md`에 남깁니다.

추가 메뉴 fixture는 `grain_salad`로 정의합니다.
원재료는 채소 1·곡물 1, 중간 재료는 `prepped_grain_salad`, 프렙 노동량 1, 손질 30 tick, 냉식 조리 100 tick, 매출 700, 대기 한도 500 tick을 사용합니다.
기존 수거·손질·조리·제공을 조합하며 메뉴·중간 재료·시나리오 데이터만 추가합니다.
추가한 이름·재료·프렙이 화면과 내보낸 팩에 나타나고 실제 주문이 제공되는지 검사합니다.
검증을 통과시키기 위한 해당 메뉴 전용 분기를 시뮬레이션이나 UI에 추가하지 않습니다.

M2-09의 고정 비교는 다음 네 축으로 실행합니다.
기본은 프렙 0·M1 배치·우선순위 1입니다.
프렙 비교는 구이 2개만 미리 준비합니다.
배치 비교는 다른 조건을 그대로 두고 출고대를 타일 `(8, 5)`, 작업 위치 `(8, 4)`로 옮깁니다.
우선순위 비교는 구이 주문 도착 다음 tick에 우선순위를 2로 설정하고 다른 주문은 1로 둡니다.
결합 비교는 이 세 선택을 함께 사용합니다.
노동량·경로·누적 시간에서 각 선택의 효과를 확인하고, 적어도 하나의 비교에서 제공 수 또는 손익 차이를 얻어야 합니다.
차이가 없으면 근거와 조정안을 기록하고 fixture나 규칙을 몰래 바꿔 통과시키지 않습니다.

다음 명령을 M2 구현 계약으로 추가합니다.
현재 기준 커밋에는 `m2` suite와 `capture_m2.gd`가 없으므로 아직 실행 가능한 검사나 통과 결과가 아닙니다.

```bash
export GODOT_BIN=/Applications/Godot.app/Contents/MacOS/Godot
bash scripts/check.sh m0
bash scripts/check.sh m1
bash scripts/check.sh m2
bash scripts/check-export.sh
"$GODOT_BIN" --path . --script tests/capture_m2.gd
```

CI는 같은 `check.sh m0`, `check.sh m1`, `check.sh m2`, `check-export.sh`를 사용합니다.
`check-export.sh`는 기존 M1 팩 검사를 유지하고 M2 준비 확정·첫 주문과 추가 메뉴 fixture도 검사합니다.
실제 iOS 앱의 `.pck`를 인자로 주는 기존 경로도 유지합니다.
스크립트 오류, assertion 실패, 필수 완료 표지 누락은 실패로 처리합니다.
규칙 회귀는 의도한 잘못된 구현이나 입력에서 먼저 실패한 것을 확인합니다.

M1의 기존 콘텐츠·규칙·결정론 검사는 모두 유지합니다.
새 snapshot 필드 때문에 hash 값 자체가 달라질 수 있지만 같은 엔진·콘텐츠·시뮬레이션 버전과 입력의 일치는 계속 필수입니다.
M1 기본 영업의 제공 16건, 만료 4건, 매출 14600, 손익 6000은 유지합니다.

## 11. 모바일과 사용자 증거

iPhone은 기존 기준 기기의 개발 앱에 새 빌드를 덮어 설치합니다.
설치와 실행은 각각 사전에 고지하며 앱 삭제는 하지 않습니다.
Android와 iOS export는 한 번에 하나씩 실행하고 소스 SHA·앱 팩 SHA·설치 결과를 기록합니다.
기존 M0 수동 관찰을 반복 요구하지 않고 M2의 새 준비 조작·마감 분석·재준비를 확인합니다.
Android의 실기기 검증은 구매 후에 수행하며 export 성공과 구분합니다.

사용자 관찰은 개인정보 대신 참가자 번호로 기록합니다.
각 기록에는 빌드 SHA, 기기, 첫 시도 준비 선택, 종료 결과, 자발적 재도전 여부, 설명한 개선 가설, 두 번째 선택, 막힌 조작을 포함합니다.
운영자나 에이전트의 반복 실행은 처음 접한 사용자 5명으로 세지 않습니다.
참가자에게 메시지를 보내거나 모집하는 일은 이 PR의 외부 실행 권한에 포함하지 않습니다.

코드 PR의 완료와 M2 통과를 구분합니다.
명세의 구현·자동 검사·현재 head 리뷰·가용한 iPhone 조작 확인을 완료하면 구현 PR을 머지할 수 있습니다.
M2 통과는 M2-13의 실제 사용자 기록과 제작성 증거가 갖춰진 뒤 판단합니다.
사람의 관찰이 없으면 보류로 남기며 M3에 착수하지 않습니다.

## 12. 설계 근거와 승인

Oracle의 개인 계정 프로젝트 조회에서 `prep`, `placement`와 관련된 적용 가능한 선례는 `[no precedent found]`였습니다.
전역 도구 배치 자료는 주방 배치 규칙의 근거로 사용하지 않았습니다.

승인 범위는 메뉴별 1인분 중간 재료, 준비 노동량 6, 위의 손질 시간, 탭 기반 설비 이동·회전, 마감 시간 집계와 PR·사용자 검증의 분리입니다.
이 계약으로 `$pr-loop` 구현·검증·리뷰를 진행합니다.
