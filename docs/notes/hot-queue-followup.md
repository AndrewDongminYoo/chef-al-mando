# 화구 앞 대기 진단과 iPhone 설치

2026-09-09에 PR #10의 머지 커밋 `aff1826b5563d6eb98a06e8dec8abf69446b3d33`을 로컬 `main`에 반영했습니다.
운영자는 다음 작업과 현재 앱 설치를 요청했고, 화구 앞 대기의 주문량으로 목표를 달성할 수 없다고 보고했습니다.
추가 제보의 입력 결함은 네 번째 절에, 승인한 메뉴별 기본 우선순위 보완은 마지막 절에 기록했습니다.
앞선 세 절은 14:37 설치 당시의 진단과 검증 기록입니다.

## 진단과 변경

현재 콘텐츠는 총 주문 20건, 제공 목표 14건, 손익 목표 1,500입니다.
실제 3000 tick 영업에서 기본 운영은 제공 7건·시간 초과 13건·손익 -3,350이었습니다.
`tests/fixtures/m3_policies.gd`의 기준 운영은 제공 15건·시간 초과 5건·손익 9,250으로 두 목표를 충족했습니다.
주문 수가 목표보다 적은 현상은 재현하지 못했습니다.

iPhone에서 읽은 기록에는 화구 앞 대기의 최고 제공 10건, 최고 손익 550, 미완료 상태가 있었습니다.
두 최고 기록은 독립적인 값이며 동일한 시도의 결과라는 뜻은 아닙니다.
이 기록에는 개별 시도의 주문 일정·준비 선택·명령 로그가 없으므로, 운영자가 겪은 시도의 정확한 원인은 `[UNCERTAIN]`입니다.

기존 영업 요약은 제공 건수만 표시했습니다.
이제 실제 도착한 주문 수와 전체 주문 수, 제공·미제공·취소 건수를 함께 표시합니다.
화구 앞 대기 안내에는 구이 프렙, 동선 단축, 주문 우선순위와 시간 초과의 의미를 보강했습니다.
한국어·영어 문구를 함께 변경했으며 목표·주문 일정·시뮬레이션 규칙·저장 버전은 유지했습니다.

기본 배치에서 검증한 운영은 구이 4건 프렙, 냉식대 왼쪽 2칸, 화구 왼쪽 3칸, 제공대 왼쪽 5칸 이동입니다.
직원은 전체 담당으로 두고 구이 주문의 우선순위를 2로 설정합니다.
이 정책은 자동 시뮬레이션과 실제 장면의 명령 경로로 검증했으며 실기기 수동 완주 결과는 아닙니다.

개인 계정의 `chef-al-mando`를 대상으로 Oracle에 `scenario goals`, `order schedule`을 조회한 결과는 `[no precedent found]`였습니다.
현재 콘텐츠와 실제 실행 결과를 기준으로 변경 범위를 정했습니다.

## 추가 제보: 우선순위 입력 유실

운영자는 안내한 준비를 적용해도 제공 9건·손익 -350이며 우선순위 버튼이 잘 반응하지 않는다고 보고했습니다.
동일한 준비에서 우선순위 명령을 제외한 실행도 제공 9건·손익 -350이었습니다.
이후 iPhone의 실제 마감 저장을 새 PCK로 복원해 같은 제공 수와 손익을 확인했습니다.
확인한 저장의 배속은 4배였고, 구이 주문 10건 중 우선순위 2가 반영된 주문은 `order_03` 한 건이었습니다.

`presentation/main.gd`의 `_show_selected_order`는 매 갱신마다 동작 버튼을 비활성화한 뒤 다시 활성화했습니다.
Godot viewport에 실제 누름 이벤트를 넣고 손을 떼기 전에 영업을 진행하면 버튼의 눌림 상태가 풀리고 명령이 유실됐습니다.
수정 전에는 눌림 유지·명령 생성·표시·시뮬레이션 반영 검사 네 곳이 실패했습니다.
최종 활성 상태를 한 번만 설정하도록 수정한 뒤 통과했습니다.
대기 중인 우선순위도 상세와 주문 행에 즉시 표시하며, 실제 시뮬레이션 반영은 기존대로 다음 tick에 수행합니다.

최소 입력 회귀 명령은 `GODOT_BIN=/Applications/Godot.app/Contents/MacOS/Godot bash scripts/check.sh m1`입니다.
M1은 1배·4배에서 누른 채 시간을 진행하는 입력 회귀를 포함해 190건, M3는 실제 주문 행·우선순위 버튼으로 영업을 진행하는 회귀를 포함해 732건, M4는 저장·화면 회귀 1,085건이 통과했습니다.
M3의 1배속 버튼 입력 완주는 제공 15건·손익 9,250입니다.
명령을 직접 넣지 않고 각 구이 주문의 행과 우선순위 버튼을 눌렀으며, 각 누름에 0.2초를 진행한 뒤 뗐습니다.
누름 유지·명령 한 건·표시 값·반영 값·해제 상태를 읽었습니다.
검증 로그는 `priority-input-red.log`, `priority-input-final-m1.log`, `priority-input-final-m3.log`, `priority-input-m4.log`입니다.

### 남은 타이밍 문제

같은 버튼 조작에 4배속을 적용하면 각 0.2초의 누름 동안 8 tick이 흐릅니다.
이 조건에서는 우선순위 명령이 모두 반영돼도 제공 9건·손익 -350으로 목표에 미달했습니다.
기존 1배·4배 결정론 검사는 같은 게임 tick에 같은 명령을 적용하는 계약이며, 실제 시간 기준 조작 지연까지 같다는 뜻은 아닙니다.
앞선 공략은 입력 시점에 민감했으며 4배속의 수동 조작 성공을 보장하지 않습니다.
관련 실패 근거는 `build/check/priority-playthrough-4x.log`입니다.

기준 예시와 확인한 저장의 두 배치에서 유효한 프렙 조합 156개, 구이 4건 프렙을 사용하는 유효 배치 120개를 추가로 실행했습니다.
이 탐색 범위에서는 영업 중 우선순위 변경 없이 목표에 도달한 조건이 없었습니다.
이는 모든 배치·프렙 조합이 불가능하다는 증명이 아닙니다.
근거는 `hot-queue-preparation-probe.log`, `hot-queue-layout-probe.log`입니다.
준비 단계에서 메뉴별 기본 우선순위를 정하는 방식은 후속 설계 제안이며 이번 수정에 구현하지 않았습니다.

macOS 전역 마우스 주입 검사는 포커스 중단과 간헐적인 입력 유실로 완주 근거로 사용할 수 없었습니다.
Advisor의 검토에 따라 viewport 입력으로 실제 Godot 버튼 경로를 검사했고, 렌더링·OS 입력·iPhone의 실제 터치를 같은 증거로 취급하지 않았습니다.
개인 프로젝트의 `button disabled`, `touch refresh` Oracle 조회 결과는 `[no precedent found]`입니다.

## 승인한 메뉴별 기본 우선순위 보완

운영자는 준비 화면에 메뉴별 기본 우선순위를 추가하는 제안을 승인했습니다.
계약은 [메뉴별 기본 우선순위](../specs/menu-priorities.md)입니다.
`발주·프렙` 탭의 프렙 아래에서 메뉴별 값을 `0~2`로 조절하고 요약 탭에서 확인합니다.
새 주문은 도착한 틱부터 이 값을 사용하며, 기존 주문별 조절은 유지합니다.
재도전·영업 재개는 선택값을 유지하고 준비 초기화는 모두 `1`로 되돌립니다.

새 쓰기는 schema 3이며 schema 1·2를 읽기만으로 변경하지 않습니다.
이전 준비에 기본값 필드가 없으면 모든 메뉴를 `1`로 해석합니다.
메뉴 ID와 전체 키, 정수, 범위를 검증합니다.
명령을 적용한 적이 없는 저장의 주문 우선순위는 준비 기본값과 일치해야 합니다.

### 동작과 호환성 검증

- 최초 회귀는 `preparation accepts a menu default priority`에서 실패했습니다.
  구현 후 `m4`는 1,173개 검사를 통과했습니다.
  실제 준비 버튼의 포인터 누름·뗌으로 값을 설정하며 영업 중 명령은 0건입니다.
- 같은 준비로 `1x`·`4x` 모두 제공 15건, 미제공 5건, 손익 9,250이며 최종 상태 해시가 같습니다.
  기본 정책의 화구 `(5, 2)`와 실제 저장에서 확인한 `(4, 2)` 배치를 각각 확인했습니다.
  나머지 조건은 구이 프렙 4개, 냉식 `(3, 2)`, 제공대 `(4, 5)`, 구이 기본 우선순위 `2`입니다.
- 기존 개별 주문의 덮어쓴 우선순위는 복원 객체의 값과 상태 해시로 확인합니다.
  재개 이후 도착하는 모든 주문의 기본값과 마감 해시도 비교합니다.
- 현재 iPhone 저장을 설치 예정 앱 PCK로 복원했습니다.
  이전 마감의 제공 9건·손익 -350과 상태 해시 `422dc5d024cd31a8f3a0348a9c600e915e8331398209791ead4635f4fa608aa2`가 보존됩니다.
- 보존한 이전 앱 PCK는 schema 3의 읽기와 쓰기를 `future_version`으로 거부하며 파일 바이트를 보존했습니다.
  이 검사는 schema 2를 전달했을 때 기대 실패하는 것을 먼저 확인했습니다.
- `m1` 190개, `m2` 378개, `m3` 732개, `m5` 579개 검사가 통과했습니다.
  규칙·준비·캠페인·설정·표시 경로를 확인하는 자동 검사이며 iPhone 실터치 증거는 아닙니다.
- 설치 예정 PCK 검사에서 완료 표시 7개를 확인했습니다.
  저장 핵심 검사는 기본 우선순위 `0`인 주문의 도착·복원·미래 도착·마감을 실행합니다.
- 한국어·영어와 휴대폰·태블릿의 큰 글자 화면 4개를 렌더링하고 확인했습니다.
  새 버튼의 스크롤 영역과 최소 크기, 번역된 선택값 검사는 16개를 통과했습니다.
  버튼을 영역 밖으로 옮기는 의도적인 실패 검사는 기대 메시지로 실패했습니다.
  한국어 안내의 단어가 나뉘는 것을 보고 문장을 짧게 수정했습니다.
