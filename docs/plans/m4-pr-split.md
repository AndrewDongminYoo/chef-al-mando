분할 원본은 `3325af04d3a1f196aaf3743d9bf75351a904b69a`이며 두 PR의 합류 기준은 M3 머지 커밋 `7cb8f79d540dd70334e11e3d9bed363a4b68caaa`입니다.

원본 PR의 오래된 리뷰와 검사 결과를 새 PR의 승인 근거로 사용하지 않습니다.

## 저장 핵심

브랜치는 `feat/m4-storage-core`이며 기준 브랜치는 `main`입니다.
계약은 [저장 핵심 명세](../specs/m4-storage-core.md)입니다.

- `sim/service_sim.gd`의 상태 내보내기·직접 복원과 현재 저장 정보로 증명할 수 있는 관계를 소유합니다.
- `persistence/service_session.gd`와 `campaign_store.gd`의 세션·기록 검증, 원자 교체, 백업 복구를 소유합니다.
- 기존 복원·파일 테스트와 새 명령 상태 검증표를 `m4-core`로 등록합니다.
- export 검사에는 실제 배포 팩의 복원·명령 없는 우선순위 변조 거부를 추가합니다.
- 기존 M0–M3 화면과 설정 없는 공통 harness를 유지합니다.

첫 주문 전 위치, 명령 없는 우선순위, 명령 없는 보류 담당의 P1 세 건을 하나의 불변식 보완으로 처리합니다.
같은 규칙으로 현재 담당과 명령 없는 취소 상태도 대조합니다.
전체 명령 replay, 새 저장 형식, 새 엔진, 범용 검증 프레임워크는 도입하지 않습니다.

## 화면 통합

브랜치는 `feat/m4-presentation`이며 처음에는 저장 핵심 브랜치를 기준으로 하는 종속 PR로 만듭니다.
저장 핵심이 머지되면 실제 합류 상태를 확인하고 기준을 `main`으로 전환합니다.

- `main.gd`, `campaign_screen.gd`의 checkpoint·이어하기·실패·마감 흐름을 소유합니다.
- 설정 파일, 번역, 글자 크기, 오디오와 폰·태블릿 화면을 소유합니다.
- 화면 테스트, 설정을 포함한 새 프로세스 검사, 렌더링 기록과 전체 M4 runner를 소유합니다.
- 공통 harness와 export·CI 연결은 저장 핵심의 검사도 유지하도록 통합합니다.

공유 파일은 최종 변경 내용을 기준으로 추출하며 기존 커밋을 무조건 cherry-pick하지 않습니다.
최종 화면 통합 트리와 분할 원본을 비교해 의도한 저장 보완·검증·문서 외의 변경이 없는지 확인합니다.

## 검사와 종료 조건

1. 저장 핵심은 실제 생성한 상태의 변조 RED를 확인한 뒤 정상·변조 상태와 실제 파일 복구를 검사합니다.
2. M0–M3 회귀, `m4-core`, export 실패 처리, 새 PCK의 저장 핵심 실행을 통과해야 합니다.
3. 화면 통합은 `m4-core`와 전체 M0–M4, 새 프로세스 복원, export 실패 처리와 PCK 검사를 통과해야 합니다.
4. 각 PR의 현재 커밋을 독립 리뷰하고 실제 CI 결과를 확인합니다.
5. 후속 hosted 리뷰는 각 PR에서 한 회를 기본 범위로 두고, 새 영역의 지적을 계속 추가하는 발견 절차로 사용하지 않습니다.
6. 두 PR의 실제 머지 커밋과 최종 통합 내용을 확인한 뒤 기존 PR #7을 닫습니다.

Godot은 버전 확인과 자식 프로세스를 포함해 `--headless`로만 실행합니다.
새 화면 캡처·포커스 변경·모바일 기기 쓰기는 이번 분할에 포함하지 않습니다.
Android 실기기와 사용자 5명 검증 보류를 유지합니다.
