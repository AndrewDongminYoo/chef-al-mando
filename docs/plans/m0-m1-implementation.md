# M0·M1 구현 계획

작성일: 2026-09-07 · 상태: 구현 승인, M0 선행 작업 착수

## 1. 목표와 시작 조건

[M0·M1 명세](../specs/m0-m1.md)를 구현하여 양 플랫폼 실행과 결정론적인 한 번의 영업을 검증합니다.
[전체 블루프린트](PLAN.md)의 M0 → M1 순서와 초기 7 작업일 예산을 유지합니다.
Android 실기기는 현재 없으며 구매 예정입니다.
2026-09-07 구현 승인에 따라 AGENTS의 기준 실기기 확정 조건에 제한된 예외를 적용하여 데스크톱·iPhone·export 준비를 먼저 수행합니다.
이 예외는 M0 통과 조건이나 M0 → M1 의존성을 바꾸지 않습니다.

이번 산출물은 명세와 구현 계획입니다.
구현 단계의 `$pr-loop` 실행은 승인된 명세를 brief로 사용하며 각 단계의 실제 diff에 맞춰 검증·리뷰 범위를 정합니다.
M0를 통과하기 전에는 M1 소스를 구현하지 않습니다.
커밋·push·PR·merge 결과가 실기기 통과를 대신하지 않습니다.

## 2. 변경 범위와 구조

새 의존성 없이 Godot 내장 기능과 typed GDScript로 시작합니다.
초기에는 다음 책임 단위만 만들고 필요한 데이터 객체는 가까운 파일에 둡니다.
파일 분리는 실제 책임이 커질 때만 수행합니다.

| 단계 | 주요 파일 또는 디렉터리                                                     | 책임                                  |
| ---- | --------------------------------------------------------------------------- | ------------------------------------- |
| M0   | `project.godot`, `export_presets.cfg`, `.gitignore`                         | main scene, 화면, export, 생성물 제외 |
| M0   | `presentation/main.tscn`, `presentation/main.gd`                            | 빈 주방과 터치 UI                     |
| M0   | `platform/app_lifecycle.gd`                                                 | 배경 정지와 수동 재개                 |
| M0   | `scripts/check.sh`, `tests/run_tests.gd`, `tests/test_m0.gd`                | 버전·파싱·최소 scene 검사             |
| M0   | `.github/workflows/check.yml`                                               | 로컬과 동일한 headless 검사           |
| M1   | `content/definitions.gd`, `content/m1_first_service.tres`                   | 정적 정의, 고정 fixture, 유효성 검사  |
| M1   | `sim/service_sim.gd`, `sim/grid_routes.gd`                                  | tick·명령·주문·배정·경제와 정적 경로  |
| M1   | `presentation/tick_driver.gd`, `presentation/main.gd`                       | tick 공급과 준비·영업·마감 표시       |
| M1   | `tests/test_content.gd`, `tests/test_rules.gd`, `tests/test_determinism.gd` | fixture·경계·경로·결정론              |
| 공통 | `docs/notes/m0-verification.md`, `docs/notes/m1-verification.md`            | 실제 실행 시 명령·기기·SHA·결과 기록  |

경로는 구현 책임 제안이며 현재 존재한다는 뜻이 아닙니다.
M1에는 `persistence/` 구현, 캠페인 모델, 프렙·배치 편집기, 아트 파이프라인을 추가하지 않습니다.

## 3. 작업 순서와 검증

### P0. 환경 기준 확인

- [ ] Android 기기 구매 후 기종·OS·가용성을 명세에 반영합니다.
- [x] `.godot-version`의 엔진과 동일 버전 템플릿의 출처·체크섬을 확인합니다.
- [x] Android SDK·JDK와 개인 Apple 개발 서명의 가용성을 확인합니다.
- [x] 설치한 바이너리와 템플릿 버전을 실행 기록에 남깁니다.

검증: `"$GODOT_BIN" --version`, `xcodebuild -version`, `adb devices -l`, `xcrun devicectl list devices`와 템플릿 파일 확인입니다.
이 단계의 출력은 환경 가용성만 증명하며 앱 실행을 증명하지 않습니다.
템플릿을 확보할 수 없거나 서명·기기가 없으면 M0를 미통과로 유지합니다.
준비 작업 예외가 승인되면 Android 기기 확정만 대기 상태로 두고 P1과 P2의 실행 가능한 부분을 진행합니다.
P2 전체 통과 전에는 P3에 착수하지 않습니다.

### P1. M0 실행 화면과 검사 기반

- [x] 빈 주방 scene, 가로 화면, 안전 영역, 한국어 버튼을 추가합니다.
- [x] 시작·정지·재개 카운터와 생명주기 어댑터를 연결합니다.
- [x] 테스트 runner와 `scripts/check.sh m0`를 추가합니다.
- [x] 잘못된 scene 참조와 빈 suite가 검사를 실패시키는지 확인합니다.
- [x] CI가 고정 엔진으로 같은 wrapper를 실행하도록 구성합니다.

검증: `bash scripts/check.sh m0`로 버전·scene 로드·어댑터 동작을 확인합니다.
실제 터치와 안전 영역은 다음 단계의 기기 화면으로 확인합니다.
새 CI action을 사용할 경우 개인 저장소 정책에 따라 commit SHA를 고정합니다.

### P2. M0 양 플랫폼 export와 실제 실행

- [x] Android·iOS debug preset과 생성물 제외 경로를 구성합니다.
- [x] 명세의 export 명령으로 APK와 Xcode 프로젝트를 생성합니다. iOS 출력 경로는 명세의 `build/ios/` 대신 `build/ios-final/`을 사용했고 산출물 SHA는 기록하지 않았습니다.
- [x] export된 iOS scheme과 서명 설정에 맞는 빌드 명령을 기록합니다.
- [ ] 양 실기기에서 M0-01부터 M0-05까지 확인합니다.
- [ ] 증거를 기록한 뒤에만 M0 통과를 표시합니다.

검증: 명세의 export 명령과 양 기기의 터치·가로 방향·10초 배경 전환 절차입니다.
실제 빌드 명령, 종료 코드, 엔진·템플릿, SHA, 기종·OS, 화면 증거, 실패 항목을 기록합니다.
Mac mini에서는 먼저 `uptime`으로 부하를 확인하고 Android와 Xcode 빌드를 하나씩 실행합니다.
개인 iPhone의 각 쓰기 작업은 실행 전에 별도로 알립니다.

### P3. M1 콘텐츠와 상태 전이

- [ ] 정적 정의와 메뉴·재고·설비·직원·20건 일정을 데이터로 추가합니다.
- [ ] 명세의 표와 생성 일정을 비교하는 콘텐츠 검사를 작성합니다.
- [ ] 주문 도착·만료·종료 상태와 정수 손익을 구현합니다.
- [ ] tick 3000 종료와 기한·완료 충돌 테스트를 작성합니다.

검증: `bash scripts/check.sh m1`의 콘텐츠·시간·경제 테스트입니다.
필수 suite 이름을 초기부터 등록하고 아직 구현하지 않은 검사는 통과나 skip으로 처리하지 않습니다.
P3~P5 중에는 전체 M1 gate가 미통과일 수 있으며, 작업별 검사 결과와 전체 결과를 구분합니다.

### P4. 배정·이동·취소

- [ ] 원재료·설비·직원 확보를 원자적 배정으로 구현합니다.
- [ ] 정수 이동, 중간 결과물 위치, 공정 인계와 담당 변경을 연결합니다.
- [ ] 취소·만료·경로 실패 시 예약 해제와 소비 보존을 구현합니다.
- [ ] 재료 부족·담당 없음·작업대 사용 중·경로 없음 표시 상태를 만듭니다.

검증: 명세 M1-04~M1-09의 유발 fixture로 예약·소비·종료 불변식을 확인합니다.
직원·작업대당 활성 배정 1개 이하, `0 <= reserved <= on_hand`, 종료 주문 매출 불변을 매 tick 검사합니다.
두 직원의 같은 통로 통과와 작업 위치 독점을 별도로 검사합니다.

### P5. 플레이 루프와 결정론

- [ ] 준비·영업·마감 화면을 시뮬레이션 상태에 연결합니다.
- [ ] 명령 sequence, 정지 중 예약, 배속 tick 공급기를 구현합니다.
- [ ] 고정 로그에 우선순위·담당·취소를 포함하여 기록합니다.
- [ ] 같은 로그 반복과 1배·4배 상태 해시 비교를 연결합니다.
- [ ] 기본 20건 fixture의 최종 매출·손익·제공 결과를 실제 실행으로 기록합니다.

검증: `bash scripts/check.sh m1` 전체와 명세 M1-01~M1-11입니다.
순수 시뮬레이션을 두 번 반복하는 검사 외에 실제 tick 공급기에 서로 다른 프레임 간격을 넣어 같은 3000 tick 결과를 비교합니다.
큰 프레임 간격에서도 처리 상한 이후 남은 tick이 유실되지 않는지 검사합니다.
초기 해시는 계산 결과로 기록하며 미리 임의의 값을 기대값으로 만들지 않습니다.

### P6. M1 모바일 완주와 검토

- [ ] 양 플랫폼에서 새 M1 빌드를 export하고 설치합니다.
- [ ] 메뉴 3종의 제공, 우선순위·담당·취소, 정지·재개, 마감·재시작을 확인합니다.
- [ ] 영업 중 배경 전환 후 상태와 정지 유지 여부를 확인합니다.
- [ ] M1-12 증거와 전체 검사 결과를 기록합니다.
- [ ] 명세와 실제 구현의 차이를 검토하고 M1 통과 여부를 결정합니다.

검증: `bash scripts/check.sh m0`, `bash scripts/check.sh m1`, 양 실기기의 M1-12입니다.
명세에 맞는 전체 변경을 한 번 검토하며 실제 diff 크기와 핵심 변경 여부에 따라 리뷰 깊이를 정합니다.
M1 통과 후에만 M2 프렙·배치·재미 검증을 시작합니다.

## 5. 위험과 완료 조건

예약 시점과 소비 시점을 섞으면 취소 후 재고가 늘거나 이중 차감될 수 있습니다.
첫 pickup 배정과 시작을 구분하는 명세·회귀 테스트를 먼저 적용합니다.
공정 인계 중 결과물 위치를 생략하면 이동이 순간적으로 끝날 수 있으므로 해당 위치도 시뮬레이션 상태와 해시에 포함합니다.
기기 미확보와 export template 부재는 실제 M0 차단 조건이며 데스크톱 실행으로 대체하지 않습니다.

문서 완료 기준은 M0·M1 범위, 20건 fixture, 경계 규칙, 명령 계약, 단계별 수용 기준을 서로 연결하는 것입니다.
구현 완료 기준은 명세의 M0-01부터 M0-05까지와 M1-01부터 M1-12까지를 실제로 통과하는 것입니다.
현재 M0 로컬 구현·검사와 양 플랫폼 export를 완료했습니다.
iPhone 설치·프로세스 실행은 확인했지만 양 플랫폼 실기기 수용 기준은 아직 통과하지 않았습니다.
세부 근거는 [M0 실행 기록](../notes/m0-verification.md)에 구분하여 기록합니다.

Oracle 조회는 `[no precedent found]`였으며 기존 프로젝트 선례를 가정하지 않았습니다.
정확한 기술 근거와 환경 관찰은 명세의 환경·근거 절에 기록했습니다.
