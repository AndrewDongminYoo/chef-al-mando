# Chef al Mando 제품·기술 블루프린트

- 작성일: 2026-09-06
- 확정일: 2026-09-07
- 버전: 0.1
- 상태: 확정 기준

## 0. 문서의 역할

이 문서는 구현 완료 보고서가 아니라 제품 방향, 시스템 경계, 단계별 검증 기준을 정의하는 기준 문서입니다.
이 문서의 확정은 탑다운 가로 화면, 시나리오형 진행, 직원 통과 규칙, Godot 기반 구조를 포함한 제품·기술 방향을 승인한다는 뜻입니다.
이후 이 방향을 바꾸려면 변경 이유와 영향을 이 문서에 기록하고 별도로 승인해야 합니다.

콘텐츠 수량은 v1 상한이자 초기 제작 목표입니다.
가격 6,600원은 출발 가설입니다.
성능 목표와 플레이테스트 통과 조건은 검증 기준이며 이미 달성된 실측 결과가 아닙니다.
출시 플레이타임과 출시일은 실측 전에 약속하지 않습니다.

블루프린트 확정 당시 저장소에는 초기 Godot 프로젝트와 기본 아이콘이 있었습니다.
당시 `project.godot`은 `4.7` 기능 태그와 `GL Compatibility`를 선언했지만, 정확한 안정판과 동일 버전 export template은 M0 기준으로 고정되지 않았습니다.
현재 구현 상태와 고정 환경은 [README](../../README.md)와 [M0·M1 구현 명세](../specs/m0-m1.md)에서 확인합니다.
이번 블루프린트 확정은 코드 구현, 외부 서비스 설정, 마일스톤 통과를 주장하지 않습니다.

### 확정한 방향

- 오프라인 선불형 2D 주방 경영 게임을 만듭니다.
- iOS와 Android 휴대폰·태블릿을 v1 플랫폼으로 삼습니다.
- 가로 화면 탑다운 시점을 사용합니다.
- 고정된 시작 조건을 가진 시나리오형 캠페인을 사용합니다.
- 실시간 진행과 언제든지 사용할 수 있는 일시정지를 함께 제공합니다.
- 직원은 서로 통과할 수 있으며 작업 위치만 독점합니다.
- Godot 4.x Standard와 typed GDScript를 사용합니다.
- 고정 tick 기반의 결정론적 시뮬레이션을 프레젠테이션에서 분리합니다.

### M0~M1 구현 명세에서 고정할 항목

- 정확한 Godot 안정판과 export-template 버전
- 기준 iPhone과 Android 실기기
- 메뉴 3종과 주문 20건 fixture
- 로컬·CI 검증 명령과 증거 형식
- 프레임별 tick 처리 상한을 측정하기 위한 초기 계측 방식

이 항목이 포함된 구현 명세를 승인하기 전에는 M0~M1 코드를 구현하지 않습니다.

## 1. 제품 한 문장

작은 레스토랑의 셰프가 되어 제한된 재료, 작업대, 인력으로 영업을 준비하고, 밀려오는 주문의 우선순위를 조정하며, 하루의 병목을 개선하는 오프라인 2D 경영 시뮬레이션입니다.

핵심 경험은 빠른 탭이 아니라 준비와 지시가 맞아떨어져 주방이 원활하게 돌아가는 만족감입니다.
요리사 경험은 레시피 수를 늘리는 데보다 프렙, 작업대 경쟁, 동선, 주문 묶음 처리의 현실적인 선택을 만드는 데 활용합니다.

## 2. 제품 원칙과 대상

- 대상은 손놀림 경쟁보다 운영과 최적화를 즐기는 모바일 플레이어입니다.
- 요리 지식이 없어도 첫 영업을 이해할 수 있어야 합니다.
- 실시간으로 진행하지만 언제든지 일시정지할 수 있어야 합니다.
- 플레이어에게 계획할 시간을 빼앗지 않습니다.
- 손해에는 읽을 수 있는 원인이 있어야 합니다.
- 직원이 기다리는 이유를 항상 표시합니다.
- 현실의 복잡함은 의미 있는 선택을 만들 때만 도입합니다.
- 실제 식당 운영 교육이나 위생 지침을 제공하는 제품으로 만들지 않습니다.
- 한 번 구매하면 시작부터 엔딩까지 플레이할 수 있어야 합니다.
- 광고, 에너지, 가챠, 접속 보상, 강제 계정을 넣지 않습니다.
- 짧은 영업을 반복하며 개선하게 합니다.
- 실패하면 같은 조건으로 재도전할 수 있게 합니다.

초기 플랫폼은 iOS와 Android 휴대폰·태블릿입니다.
개발 중 데스크톱 실행은 허용하지만 PC 스토어, 웹, 콘솔 출시는 v1 약속에 포함하지 않습니다.
가격은 6,600원을 출발 가설로만 유지하고 콘텐츠와 플레이테스트 결과를 확인한 뒤 확정합니다.

## 3. 플레이 루프

1. 브리핑에서 예상 주문 구성, 예산, 이번 영업의 필수 목표를 읽습니다.
2. 준비 단계에서 메뉴, 재료 구매, 직원 담당, 설비 배치, 사전 손질량을 정합니다.
3. 영업 중에는 주문 유입, 재료 확보, 조리, 패스 제공이 이어집니다.
4. 플레이어는 담당, 우선순위, 주문 취소를 조절합니다.
5. 마감 화면에서 매출, 재료비, 인건비, 폐기, 제공률, 지연 원인을 확인합니다.
6. 같은 영업을 재도전하거나 다음 시나리오로 넘어갑니다.

대표 딜레마는 다음과 같습니다.
수익이 높은 구이 주문을 먼저 처리하면 화구를 오래 점유합니다.
짧은 메뉴부터 처리하면 제공률은 높아지지만 고수익 주문이 이탈할 수 있습니다.

정답이 빠른 탭 하나로 수렴하면 설계를 수정합니다.
같은 주문 조건에 서로 다른 정책을 적용했을 때 결과나 설명 가능한 병목이 달라져야 합니다.

| 구분 | 출시 기준                                          | 제외                                         |
| ---- | -------------------------------------------------- | -------------------------------------------- |
| 공간 | 하나의 레스토랑 테마, 주방 레이아웃 3종            | 다점포, 건물 층, 오픈월드                    |
| 진행 | 튜토리얼을 포함한 시나리오 8개, 마지막 영업과 엔딩 | 무한 경제, 절차 생성 캠페인                  |
| 음식 | 메뉴 8종, 재료 12종 이내, 기존 공정 조합           | 자유 레시피 편집, 실제 레시피 가져오기       |
| 직원 | 동시 최대 4명, 담당·조리 숙련도                    | 인간관계, 개별 서사, 복잡한 피로 모델        |

콘텐츠 수량은 상한이자 초기 목표입니다.
M2에서 제작 비용을 측정한 뒤 줄일 수 있습니다.
출시 플레이타임은 실측 전 약속하지 않습니다.
시나리오 8개만으로 구매 가치가 부족하면 반복 숙련 목표를 개선하거나 상품 규모를 재판단합니다.

캠페인은 시나리오별 고정 시작 예산과 재고를 사용합니다.
앞선 실패가 누적되어 진행이 불가능해지는 구조를 피합니다.
클리어 기록과 최고 성과는 유지하지만 다음 시나리오의 현금을 무제한으로 증폭시키지 않습니다.

## 5. 핵심 시스템 규칙

### 5.1 시간과 주문

- 기본 영업 길이는 게임 시간 300초입니다.
- 일시정지와 `1x`, `2x`, `4x` 배속을 제공합니다.
- 실제 세션 길이는 준비와 일시정지 사용량에 따라 달라집니다.
- 주문은 시나리오 seed로 생성한 일정에 따라 들어옵니다.
- 주문 도착 시각, 메뉴, 대기 한도는 시뮬레이션 상태입니다.
- 주문 상태는 접수, 작업 중, 제공, 취소, 기한 초과 중 하나입니다.
- 종료 상태에서는 다시 매출이 발생하지 않습니다.
- 주문의 기한 tick이 되면 먼저 만료시킵니다.
- 같은 tick에 작업이 완료되어도 제공 성공으로 인정하지 않습니다.
- 게임 시간이 300초에 도달하면 영업을 종료합니다.
- 미완료 주문은 미제공으로 정리합니다.
- 이미 소비한 재료는 되돌리지 않습니다.
- 연장 영업은 v1에 포함하지 않습니다.

### 5.2 재료와 프렙

- 재료 수량은 정수 단위로 계산합니다.
- 금액은 정수 최소 화폐 단위로 계산합니다.
- 준비 단계의 프렙은 제한된 준비 노동량을 소비해 중간 재료를 만듭니다.
- 초기에는 별도 실시간 프렙 화면을 만들지 않습니다.
- 영업 중 공정을 시작할 때 필요한 재료를 한 번만 차감합니다.
- 작업이 대기 중이라는 이유만으로 재료를 소비하지 않습니다.
- 공정 시작 전에 주문을 취소하면 예약만 해제합니다.
- 공정 시작 후 주문을 취소하면 이미 소비한 재료를 손실로 처리합니다.
- M1에서는 주문 시작 시 전체 원재료를 확보하는 단순 레시피만 사용합니다.
- M2에서는 중간 재료 공정으로 확장합니다.
- 초기 재고는 해당 영업에서 구매한 것으로 처리합니다.
- 영업 사이에는 재고를 이월하지 않습니다.
- 마감 잔량은 폐기 내역으로 표시합니다.
- 영업 손익은 제공 매출에서 구매 재료비와 고정 인건비를 뺀 값입니다.
- 폐기 비용은 구매 비용의 부분집합이므로 다시 차감하지 않습니다.

### 5.3 직원과 작업

- 초기 공정은 재료 확보, 지정 작업대 조리, 패스 제공의 선형 순서를 사용합니다.
- 병렬 레시피 그래프와 무인 장시간 조리는 v1에 포함하지 않습니다.
- 직원은 한 번에 작업 하나만 수행합니다.
- 작업대는 한 번에 작업 하나만 허용합니다.
- 배정 순서는 플레이어 우선순위, 주문 마감 시각, 안정적인 작업 ID 순입니다.
- 담당 변경은 현재 공정을 끝낸 뒤 적용합니다.
- 즉시 중단은 명시적인 주문 취소로만 수행합니다.
- 작업대 예약과 재료 확인은 한 번의 배정 연산에서 모두 성공하거나 모두 실패해야 합니다.
- 자원의 일부만 확보한 채 무기한 대기하지 않습니다.

대기 원인은 다음 네 가지로 구분합니다.

- 재료 부족
- 담당 없음
- 작업대 사용 중
- 경로 없음

### 5.4 이동과 공간

- 사각 격자와 상하좌우 이동을 사용합니다.
- 설비 배치는 준비 단계에서만 변경할 수 있습니다.
- `AStarGrid2D`는 정적 장애물 경로를 찾는 데만 사용합니다.
- `AStarGrid2D`가 작업 예약이나 군중 교착을 해결한다고 가정하지 않습니다.
- 첫 버전에서는 직원끼리 통과할 수 있습니다.
- 설비의 작업 위치는 독점하지만 통로 타일은 독점하지 않습니다.
- 통로 예약 시스템은 보류합니다.
- 이동 거리가 생산성에 영향을 주게 합니다.
- 병목은 작업대 점유와 작업 우선순위에서 만듭니다.
- 도달할 수 없는 작업대를 만드는 배치는 준비 화면에서 차단합니다.
- 런타임 경로 실패가 발생하면 예약을 해제하고 이유를 표시합니다.

## 6. 화면과 조작

기본 시점은 가로 화면 2D 탑다운입니다.
아이소메트릭은 아트 생산성과 가림 문제를 M2에서 검증한 뒤 별도로 승인해야 합니다.

| 화면        | 플레이어가 하는 일                  | 필수 정보                       |
| ----------- | ----------------------------------- | ------------------------------- |
| 시작·캠페인 | 이어하기, 시나리오 선택             | 진행 기록, 새 게임 경고         |
| 준비        | 메뉴, 발주, 프렙, 배치, 담당 설정   | 예산, 준비 노동량, 경로 유효성  |
| 영업        | 작업 우선순위, 담당, 일시정지, 배속 | 남은 시간, 주문 마감, 대기 원인 |
| 마감        | 원인 파악, 재도전, 다음 영업        | 손익, 제공률, 대기 원인별 시간  |
| 설정        | 소리, 언어, 텍스트 크기             | 라이선스, 저장 상태             |

- 주방은 중앙에 둡니다.
- 주문 목록은 한쪽 패널에 둡니다.
- 시간 제어는 고정된 위치에 둡니다.
- 휴대폰은 선택 상세를 접이식 패널로 표시합니다.
- 태블릿은 선택 상세를 병렬 패널로 표시합니다.
- 태블릿 화면을 휴대폰 화면의 단순 확대판으로 만들지 않습니다.
- 우선순위 변경은 탭 기반 버튼을 기본으로 합니다.
- 드래그만으로 가능한 필수 조작을 만들지 않습니다.
- 상태를 색상에만 의존해서 표현하지 않습니다.
- 아이콘과 문구를 색상과 함께 사용합니다.
- 텍스트 크기, 안전 영역, 한국어 줄바꿈을 검증합니다.
- 앱이 배경으로 전환되면 자동으로 일시정지합니다.
- 앱으로 복귀해도 영업을 자동으로 재개하지 않습니다.

## 7. 기술 구조

Godot 4.x Standard와 typed GDScript를 기본으로 사용합니다.
정확한 안정판과 동일 버전 export template은 M0~M1 구현 명세에서 고정합니다.
Compatibility 렌더러로 시작하고 두 플랫폼의 실기기에서 검증합니다.
새 엔진을 학습하더라도 엔진 수정, Rust FFI, ECS, 범용 프레임워크를 먼저 도입하지 않습니다.

| 계층         | 책임                                         | 금지                                  |
| ------------ | -------------------------------------------- | ------------------------------------- |
| Simulation   | 시간, 주문, 작업 배정, 재고, 이동 진행, 손익 | UI 노드, Tween, 실제 시계에 결과 의존 |
| Content      | 메뉴, 설비, 시나리오 정적 정의와 유효성 검사 | 진행 중 상태를 공유 `Resource`에 기록 |
| Presentation | 주방, 직원, 주문, 효과음, 입력               | 애니메이션 종료로 조리 완료 판정      |
| Persistence  | 스냅샷, 백업, 버전, 복원                     | 저장 실패를 성공으로 표시             |
| Platform     | 앱 생명주기, 안전 영역, export               | 핵심 규칙을 플랫폼별로 분기           |

시뮬레이션은 `SceneTree` 없이 구동할 수 있는 `RefCounted` 기반 객체로 구성합니다.
엔진 독립 라이브러리까지 만들지는 않습니다.
UI는 명령을 제출하고 읽기 전용 상태와 이벤트를 소비합니다.
`Resource`는 정적 정의에 사용하고 런타임 상태는 별도 객체로 분리합니다.

제안 디렉터리는 `sim/`, `content/`, `presentation/`, `persistence/`, `platform/`, `tests/`, `docs/`입니다.
필요한 구현이 생길 때 해당 디렉터리를 추가하며 빈 구조만 미리 만들지 않습니다.

### 7.1 고정 tick 계약

- 초기 tick은 게임 시간 100ms입니다.
- 배속은 tick 크기가 아니라 수행 횟수를 바꿉니다.
- 명령에는 적용 tick과 순서 번호를 붙입니다.
- 같은 tick은 명령 적용, 주문 도착·만료, 작업 완료·소비 정리, 신규 배정, 이동 갱신, 이벤트 발행 순서로 처리합니다.
- 이동은 정수 진행량으로 계산합니다.
- 화면에서만 이동을 보간합니다.
- 렌더링 프레임 수와 시뮬레이션 결과를 분리합니다.
- seed만으로 결정론이 보장된다고 가정하지 않습니다.
- 명령 순서, 순회 순서, PRNG 상태를 고정합니다.
- 처리량이 부족하면 tick을 버리지 않고 실제 진행을 늦춥니다.
- 프레임별 처리 상한은 프로파일링 결과로 설정합니다.
- 결정론 보장 범위는 동일한 엔진, 콘텐츠, 시뮬레이션 버전입니다.
- 업데이트 사이의 리플레이 호환은 v1 목표가 아닙니다.

## 8. 데이터와 저장

정적 정의는 `IngredientDef`, `RecipeDef`, `StationDef`, `EmployeeDef`, `ScenarioDef`로 나눕니다.
참조에는 안정적인 문자열 ID를 사용합니다.
스프레드시트 자동 파이프라인은 필요가 확인될 때만 추가합니다.

콘텐츠 검사는 다음 조건을 실패로 처리합니다.

- 중복 ID
- 존재하지 않는 재료 참조
- 음수 수량
- 0 이하 공정 시간
- 공정 순환
- 존재하지 않는 설비 역할
- 시나리오의 판매 불가능 메뉴

새 메뉴는 지원 중인 공정을 조합할 때만 코드 변경 없이 추가할 수 있습니다.

세이브에는 다음 정보를 저장합니다.

- `schema_version`
- `content_version`
- `sim_version`
- 현재 tick
- PRNG 상태
- 주문, 직원, 작업 진행
- 재고, 예약, 이동 진행
- 캠페인 기록

모든 enum과 ID를 검증합니다.
알 수 없는 미래 버전의 세이브는 덮어쓰지 않습니다.

- 준비 완료, 마감, 명시적 종료 시점에 저장합니다.
- 플레이 중에는 일정 간격으로 안전한 tick 경계에서 저장합니다.
- 임시 파일을 쓴 뒤 검증하고 주 파일을 교체합니다.
- 마지막 정상 백업을 보관합니다.
- 플랫폼별 파일 교체 실패와 강제 종료를 테스트합니다.
- 세이브가 손상되면 백업 복구 또는 해당 시나리오 재시작을 제공합니다.
- 손상된 세이브를 자동으로 초기화하지 않습니다.
- 강제 종료 후 마지막 저장 이후의 진행 일부가 손실될 수 있음을 전제로 합니다.
- 저장을 생명주기 콜백 하나에만 맡기지 않습니다.
- M1은 시나리오 재시작만 제공합니다.
- 영업 중 이어하기는 M4에서 완성합니다.

## 9. 아트·사운드 제작 원칙

M1은 도형과 역할 색상만 사용합니다.
M2에서는 실제 크기의 직원 1명, 설비 4종, 메뉴 아이콘 3종을 적용해 가독성과 제작 시간을 측정합니다.

v1은 직원 기본 몸체와 색상 변형을 재사용합니다.
초기 모션은 4방향 이동, 작업, 대기로 제한합니다.
메뉴마다 별도의 장시간 애니메이션을 만들지 않습니다.
주문 접수, 완료, 경고 효과음을 구분합니다.
반복 경고의 재생 빈도는 제한합니다.
모든 외부 아트, 폰트, 음원은 출처와 상업 사용 권한을 기록합니다.

AI 이미지도 바로 스프라이트로 간주하지 않습니다.
방향별 일관성, 접지점, 프레임 크기, 투명 영역을 검수합니다.
아트 비용이 크면 콘텐츠 범위를 줄입니다.
자동 생성 도구를 먼저 개발하지 않습니다.

M2의 로컬 검사·선택 비교·export·기기 상태는 [M2 실행 기록](../notes/m2-verification.md)에 구분하여 기록합니다.
자동 검사나 명령 정의만으로 M2 사용자 검증이 통과했다고 판단하지 않습니다.
M3의 검증 명령과 fixture 계약은 [M3 명세](../specs/m3-campaign.md)에 정의했습니다.
캠페인 완주·저장·실제 렌더·export의 로컬 결과와 남은 수용 기준은 [M3 실행 기록](../notes/m3-verification.md)에 구분하여 기록합니다.
아직 실행하지 않은 신규 검사는 통과로 표시하지 않습니다.
M4 저장 핵심의 정확한 검증 명령은 `bash scripts/check.sh m4-core`이며 [저장 핵심 명세](../specs/m4-storage-core.md)의 상태·세션·파일·명령 관계를 검사합니다.
`python3 tests/test_export_check.py`는 필수 완료 표시 누락과 export 실패 처리를 검사하며, `bash scripts/check-export.sh`는 새 PCK에서 실제 복원·변조 거부를 검사합니다.
실행 결과는 [저장 핵심 검증 기록](../notes/m4-storage-core-verification.md)에 있습니다.
M4의 저장·새 프로세스·현지화·화면·export 검증 명령은 [M4 명세](../specs/m4-mobile.md)에 정의했습니다.
실제 실행 결과와 실기기 수용 한계는 [M4 검증 기록](../notes/m4-verification.md)에 구분하여 기록합니다.
M5의 검증 명령과 배포 빌드 수용 형식은 [M5 명세](../specs/m5-release-candidate.md)에 정의했습니다.
검사 정의와 로컬 통과만으로 실제 다운로드 빌드의 수용을 주장하지 않습니다.
Android 실기기는 구매 예정이며 Android 기종·OS 확정과 실제 실행은 대기 상태입니다.
각 후속 단계의 구현 명세도 해당 단계의 코드 작업 전에 정확한 명령, fixture, 수동 증거 형식을 고정해야 합니다.
명령이 없는 상태에서 에디터 실행이나 정적 파싱만으로 마일스톤 통과를 주장하지 않습니다.

## 11. 검증 계획

### 11.1 규칙

다음 조건을 headless 시뮬레이션 테스트로 검사합니다.

- 동일 작업 중복 배정
- 재료 이중 소비
- 만료 시각과 완료 시각의 충돌
- 취소 후 예약 해제
- 마감 정산

### 11.2 결정론

고정 seed와 명령 로그를 렌더링 없이 반복합니다.
각 실행의 최종 상태 해시를 비교합니다.
`1x`와 `4x`도 동일한 게임 tick에서 비교합니다.

### 11.3 저장

활성 공정과 이동 도중에 저장하고 복원한 실행이 중단 없이 진행한 실행과 일치해야 합니다.
임시 파일 교체 실패, 강제 종료, 손상된 주 파일, 알 수 없는 미래 버전을 각각 검사합니다.

### 11.4 경로

다음 조건을 검사합니다.

- 도달할 수 없는 배치 거부
- 작업 위치 독점
- 직원 통과 허용
- 경로 실패 후 예약 해제

### 11.5 콘텐츠

모든 시나리오를 로드합니다.
정의 참조의 유효성을 검사합니다.
번역 키 누락을 검사합니다.

### 11.6 성능

M0에서 선정한 기준 Android와 iPhone에서 직원 4명, 최대 주문 부하, `4x` 조건으로 15분 동안 측정합니다.
목표는 60fps와 프레임 시간 p95 20ms 이하입니다.
이 수치는 실측 전 보장이 아닙니다.
메모리의 지속적인 증가와 tick 누적도 기록합니다.

### 11.7 CI

PR에서는 headless 파싱, 규칙, 콘텐츠 테스트를 중심으로 실행합니다.
모바일 패키징은 출시 후보 또는 배포 관련 변경에서 실행합니다.
모든 PR에 고비용 실기기 테스트를 실행하지 않습니다.

### 11.8 출시 Definition of Done

- 오프라인 첫 실행부터 엔딩까지 완주할 수 있습니다.
- 두 플랫폼에서 배경 전환·복귀와 이어하기가 작동합니다.
- 정상 세이브를 보존합니다.
- 손익 계산이 일관됩니다.
- 필수 조작을 터치로 읽고 수행할 수 있습니다.
- 콘텐츠 라이선스 기록이 있습니다.
- 사용자가 도움 없이 튜토리얼을 완료할 수 있습니다.
- 크래시와 진행 불가 차단 버그가 0건입니다.

## 12. 주요 위험과 중단 기준

| 위험                       | 최소 대응                                            | 확장 전 판단                                          |
| -------------------------- | ---------------------------------------------------- | ----------------------------------------------------- |
| 지시 없이 구경만 하는 게임 | 동일 주문에 두 정책을 적용해 결과와 선택 차이를 확인 | 결과가 같거나 이유를 읽을 수 없으면 M2에서 재설계     |
| 통로 AI에 일정 소모        | 직원 간 충돌을 제외하고 작업대 예약만 구현           | 재미에 꼭 필요하다는 관찰 전에는 통로 예약 금지       |
| Godot 학습과 모바일 차이   | 첫 단계부터 두 플랫폼 실기기 빌드                    | 엔진 문제와 게임 코드 문제를 구분해 재현              |
| 콘텐츠 양에 비해 재미 부족 | 메뉴 3종으로 재도전 검증                             | 메뉴 수를 늘려 해결하지 않음                          |
| 모바일 UI 과밀             | 접이식 상세, 일시정지, 탭 조작                       | 가장 작은 기준 화면에서 조작에 실패하면 레이아웃 수정 |
| 아트 생산 비용             | 대표 세트만 먼저 제작                                | 메뉴, 방향, 캐릭터 수를 줄임                          |
| 범용 아키텍처 과잉         | 단일 프로젝트, 간단한 명령, 별도 시뮬레이션 객체     | 프로파일 근거 없이 FFI, ECS, 자체 편집기 금지         |

중단 기준은 기능 포기가 아니라 다음 확장을 멈추고 원인을 다시 검토하는 조건입니다.
통과 조건을 충족하지 못한 상태에서 콘텐츠 수량이나 구조 복잡도를 늘리지 않습니다.

## 13. 다음 세 가지 행동

1. 이 블루프린트를 제품·기술 기준으로 사용합니다.
2. M0~M1만 구현 명세로 분리하고 정확한 엔진 버전, 기준 실기기, 메뉴 3종, 주문 20건 fixture, 검증 명령을 고정합니다.
3. 첫 실기기 빌드와 한 번의 영업 완주를 확인합니다.

첫 실기기 빌드와 한 번의 영업이 통과하기 전에는 캠페인, 브랜딩, 콘텐츠 자동화를 시작하지 않습니다.
